# 合并判据细表（yammory-tidy 参考）

本文把「这几条是不是在讲同一件事」落成可复核的对照表。判断始终由当前会话的模型做，本表只是判据清单——**逐对比较，不要凭印象批量放行**。

## 一、三档结论

对每一对（或每一组）候选，只允许三种结论：

| 结论 | 处置 |
|---|---|
| **同一件事** | 合并：一条新表述（带 `merged` 标）＋ 旧条目 `superseded` |
| **不同的事** | 什么都不做（它们各自在自己的桶里活着） |
| **互相冲突** | 什么都不做。冲突留给用户裁决，别挑一条「赢」 |

第三种最容易出错：两条都说「现在住哪」，一条 A 城一条 B 城，看着高度相似（同一主体、同一谓词、句子结构一样），但它们是**时间线上的两个状态**，不是重复。合并等于把一条记忆抹掉。

## 二、逐对检查表（按顺序问自己）

1. **两句话说的是同一个对象吗？**（同一个人 / 同一个项目 / 同一个工具）
2. **两句话说的是同一个方面吗？**（偏好 vs 能力 vs 事实 vs 约定——不同方面不合并）
3. **两句话是否互相矛盾？** 是 → 停，归「冲突」。
4. **合并后的句子需要引入原文没有的信息吗？** 需要 → 停，说明它们不是同一件事。
5. **少了一条，用户下次问起会不会丢东西？** 会 → 停，或只降级不合并（`ids` 不给 `text`）。

## 三、正面例（可合并）

| 组 | 合并后 | 判据 |
|---|---|---|
| 「偏好中文回复」／「回答尽量用中文，除非要求英文」 | 「偏好中文回复，英文仅在明确要求时使用」 | 同一主体同一谓词，后者更完整 |
| 「项目用 pnpm」／「不要用 npm 安装依赖」 | 「本项目用 pnpm 管理依赖（不用 npm）」 | 一条是另一条的特例 |
| 「周三下午没空」／「周四上午也没空」 | 「周三下午与周四上午都没空」 | 各说一半，合起来才完整 |

## 四、反面例（不许合并）

| 组 | 为什么不合并 |
|---|---|
| 「喜欢 Rust」／「不喜欢 Rust 的宏」 | 共词不共立场 |
| 「数学考了 90 分」／「数学老师姓王」 | 同领域不同事实 |
| 「现在住 A 城」／「现在住 B 城」 | 冲突（时间线上的两个状态） |
| 「答应周五交」／「周五没交」 | 承诺与事实的落差，并存才有价值 |
| 「用户是材料物理大二」／「用户 2006 年生」 | 两个独立坐标，硬并会丢可检索性 |
| 「回复用中文」／「不要替我 git push」 | 一个是风格偏好，一个是雷区；同属 user/user-global 但不同面 |

## 五、合并文本的写法

- 一句话把原意压完，可以带分号；
- **不得出现原文没有的事实**（数值、日期、偏好方向都不许新造）；
- 保留原文里最具体的限定（「除非明确要求英文」这种限定丢了，条目就变味了）；
- 坐标（`facet` / `level`）从原条目继承：几条都带同一个 `facet` 就照抄；不一致时留给用户，别硬选。

## 六、批与其边界

- 一次 `supersede` 最多 20 个 id；桶的候选超过 20 条时按计划里的 `batchHint` 分批。
- **一批只能一个桶**。桶键形如 `user/user-global #preset @C:\work\proj`，任一维不同就是另一桶。
- 一批就是一事务：任一条失败整批回滚，不会出现「改了一半」。
- 每批收尾落一行 `audit(action='consolidation')`；`/memory audit` 可查，审计里降级行的 `text` 恒为 `null`（只记 id）。

## 七、做完之后的抽查

一轮结束后值得看一眼的三个数（`/memory stats`）：

| 数 | 期望方向 |
|---|---|
| 重复率 | 下降（这正是整理的产出） |
| 召回命中率 | 不塌（合并得太狠会让按需取命中变少） |
| 注入量 | 不涨（预热段是每次会话的固定开销） |

若重复率没降、注入量反而涨，说明这轮合并产出的表述比原文还长——下次少并、并短。
