# 合并判据细表（yammory-tidy 参考）

本文把「这几条是不是在讲同一件事」落成可复核的对照表。判断始终由当前会话的模型做，本表只是判据清单——**逐对比较，不要凭印象批量放行**。

判断之后，**能否不再过人眼就落写，不由你说了算**：插件内核会拿库里的真实条目重跑一遍硬杠（`gradeMerge`），逐杠给结论。第五节是那套硬杠与三档的逐条对应。

## 一、三档结论（`MERGE_VERDICTS`）

对每一组候选，只允许三种结论：

| 结论 | 含义 | 谁能落写 |
|---|---|---|
| `auto` | **够确定**：落写不需人眼 | 只有这一档能走 `auto-tidy`（后台执行体走的就是这条） |
| `review` | **不够确定**：留成待批单子 | 走 `supersede`（过一次审批），提示里写明哪一杠没过 |
| `skip` | **不合格**：原地不动 | 什么都不做 |

第三种不算「结论」，是**不判**：字面不重合的同义句、跨桶、超条数、覆盖不足都落这里。

最容易出错的是**看着像重复、其实是冲突**：两条都说「现在住哪」，一条 A 城一条 B 城，同一主体、同一谓词、句子结构一样，但它们是**时间线上的两个状态**。合并等于把一条记忆抹掉——这类要走**分面裁决**（见第六节），不要自己挑一条「赢」。

## 二、逐对检查表（按顺序问自己）

1. **两句话说的是同一个对象吗？**（同一个人 / 同一个项目 / 同一个工具）
2. **两句话说的是同一个方面吗？**（偏好 vs 能力 vs 事实 vs 约定——不同方面不合并）
3. **两句话是否互相矛盾？** 是 → 停，归「冲突」。
4. **合并后的句子需要引入原文没有的信息吗？** 需要 → 停，说明它们不是同一件事。
5. **少了一条，用户下次问起会不会丢东西？** 会 → 停，或只降级不合并（`ids` 不给 `text`）。

## 三、正面例（可合并）

| 组 | 合并后 | 判据 |
|---|---|---|
| 「偏好中文回复」／「回答尽量用中文，除非要求英文」 | 「偏好中文回复，英文仅在明确要求时使用」 | 同一主体同一谓词，后者更完整 |
| 「项目用 pnpm」／「不要用 npm 安装依赖」 | 「本项目用 pnpm 管理依赖（不用 npm）」 | 一条是另一条的特例 |
| 「周三下午没空」／「周四上午也没空」 | 「周三下午与周四上午都没空」 | 各说一半，合起来才完整 |

## 四、反面例（不许合并）

| 组 | 为什么不合并 |
|---|---|
| 「喜欢 Rust」／「不喜欢 Rust 的宏」 | 共词不共立场 |
| 「数学考了 90 分」／「数学老师姓王」 | 同领域不同事实 |
| 「现在住 A 城」／「现在住 B 城」 | 冲突（时间线上的两个状态） |
| 「答应周五交」／「周五没交」 | 承诺与事实的落差，并存才有价值 |
| 「用户在读研」／「用户 1998 年生」 | 两个独立坐标，硬并会丢可检索性 |
| 「回复用中文」／「不要替我 git push」 | 一个是风格偏好，一个是雷区；同属 user/user-global 但不同面 |

## 五、硬杠与三档（与代码逐条对应）

出处：`lib/constants.mjs` 的 `MERGE_GATES`（杠名）、`MERGE_GRADE_LINES`（阈值）、`MERGE_VERDICTS`（档位）；判定在 `lib/consolidate.mjs` 的 `gradeMerge`。

**五根硬杠**（杠名与代码逐字一致）：

| 杠名 | 判什么 |
|---|---|
| `same-bucket` | 所有成员同属一个桶（`track × scope × agentKey`，workspace 层再加 `workspaceKey`） |
| `member-count` | 成员数在 2..5 之间 |
| `verbatim` | 成员文本与拟合并文本**去空白＋标点后逐字一致** |
| `similarity` | 两两词元 Jaccard 的**最小值** |
| `coverage` | 拟合并文本对成员词元的**最小覆盖度** |

**阈值**（`MERGE_GRADE_LINES`，保守取值：宁可多产单子，少自动合）：

| 量 | auto 线 | review 线 |
|---|---|---|
| `similarity` | ≥ 0.85 | ≥ 0.5 |
| `coverage` | ≥ 0.9 | ≥ 0.6 |

**三档怎么判出来**：

| 档 | 条件 |
|---|---|
| `auto` | 前四杠全过 **且** `similarity` / `coverage` 都达 auto 线 **且** `verbatim` 过 |
| `review` | `same-bucket` 与 `member-count` 过、相似度与覆盖度都不低于 review 线，但没达到 auto 的全部条件 |
| `skip` | 其余（跨桶、超条数、相似度或覆盖度低于 review 线） |

**关键一条**：`verbatim` 是 auto 档的**独立必要条件**。相似度再高也换不来自动合——`「…以后每次对话都要自动遵守它」` 与 `「…自动不遵守它」` 的相似度是 **0.9**（在 auto 线以上），一字之差就翻转了语义，所以它只会落 `review`，不会落 `auto`。这也是为什么**「字面只差标点或空白」几乎是 `auto` 档唯一的可达面**：改写过的同义句字面相似度通常只有 0.1～0.6 量级。

## 六、冲突 → 分面裁决（`arbitrate`）

判断归你，**裁决方向不归你**。「同一条事实、两个来源打架」时调 `memory` 工具 action=`arbitrate`，入参就是这批条目的 `ids`（工具面与 `/memory arbitrate <id...>` 命令面同一条路）。

前置条件（不满足就响亮失败，别硬凑）：

- 至少一条 `source='observation'`（观察来的）与一条其他来源（自陈来的）；
- 所有目标**共用同一个 `facet`**（七面之一）；没打面或两组面不一致 → 拒绝，不猜；
- 所有 id 同属一个桶（与 `supersede` 同一套边界）。

裁决表（代码里的唯一出处 `ARBITRATION_BY_FACET`，工具不接受反向参数）：

| 面 | 听谁 | 动作 |
|---|---|---|
| **能力与技能** | 听**观察** | 保留观察组，降级自陈组（做得到就是做得到） |
| **价值与意愿** | 听**自陈** | 保留自陈组，降级观察组（喜好只有本人说了算） |
| 躯体 / 心智 / 行为与习惯 / 社会与处境 / 经历与轨迹 | **两条都留** | 都不降级，两组各打 `gap` 标（落差本身是证据） |

同组不止一条时，取 `updatedAt` 最新者保留，其余同组条目一并降级——规则可复核，不给你挑的机会。一次审批、一批一事务；降级行审计 `text` 恒为 `null`（只记 id），另落 `arbitrate-tag`（打标）与收尾摘要行。

降级是**可回滚**的：反悔就 `memory` action=`restore`（工具面）或 `/memory restore <id...>`（命令面），`superseded → active`、`version` 不动。落差不该被抹掉，所以 coexist 面刻意一条都不降。

## 七、批与其边界

- 一次 `supersede` / `auto-tidy` 最多 20 个 id；但**分级器自己的上限是 5 条/批**（`MERGE_GRADE_LINES.maxMembers`）——超过 5 条连 `auto` 档都判不出来，所以自动整理一批最多 5 条。批量大就按计划里的 `batchHint` 分小批。
- **一批只能一个桶**。桶键形如 `user/user-global #preset @C:\work\proj`，任一维不同就是另一桶。
- 一批就是一事务：任一条失败整批回滚，不会出现「改了一半」。台账（降级行 ＋ 产出行 ＋ 摘要行）与条目在**同一个提交**里落地。
- 每批收尾落一行 `audit(action='consolidation')`；`/memory audit` 可查，审计里降级行的 `text` 恒为 `null`（只记 id）。批次号可用 `/memory restore --batch=<id>` 整批撤回。

## 八、做完之后的抽查

一轮结束后值得看一眼的三个数（`/memory stats`）：

| 数 | 期望方向 |
|---|---|
| 重复率 | 下降（这正是整理的产出） |
| 召回命中率 | 不塌（合并得太狠会让按需取命中变少） |
| 注入量 | 不涨（预热段是每次会话的固定开销） |

若重复率没降、注入量反而涨，说明这轮合并产出的表述比原文还长——下次少并、并短。

## 九、后台执行体怎么用这套判据

系统计划任务会在空闲时段唤起一个**无头会话**跑整理。那个会话与本会话用同一套硬杠、同一个库，差别只有入口：

| | 本会话（有人看着） | 后台轮（无人值守） |
|---|---|---|
| 工具动作 | `tidy` 读计划 → `supersede` 落写 | `tidy` 读计划 → **`auto-tidy`** 落写 |
| 落写门槛 | 过一次审批 | 只允许 `auto` 档；非 `auto` 一律结构化拒绝、零落盘 |
| 写入来源 | `consolidation` | **`tidy-auto`**（粒度写策略 `source:tidy-auto` 是它的放行口） |
| 被拒时的表现 | 你在场，可以改判据重来 | 留下 `*-denied` 审计行，**不要指望它换措辞重试** |

要点：

- **后台轮只做 `auto` 档**。`review` 档的组留给人在场时走 `supersede`（过一次审批），这不是遗漏，是分工。
- `auto-tidy` 的入参只有 `ids` 与 `text`——**判定由内核重跑**，调用方声明不了「这是 auto」。把 `review` 档的组塞进去只会得到一条 `INVALID_INPUT`。
- 后台轮的写入是否放行，由 headless profile 的 `writePolicies.source:tidy-auto`（`auto` / `ask` / `off`）决定；`off` 时轮次照跑、工具照调，落写被拒并留痕（按「落写」口径读「静默」：拦的是写入，不是轮次的启动）。停用与恢复：改 profile 的 `cordis.patch.yml` 里那个键（`ask` / `off` 即收口，`auto` 即放行），或停掉计划任务——都可逆。
