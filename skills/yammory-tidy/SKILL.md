# 记忆整理（yammory-tidy）🧹

把散落各处、其实在讲**同一件事**的记忆并成一条，旧条目**降级留痕**（不物理删）。

## 定位：这是负反馈回路 🔁

写入只会让记忆变多。拆掉硬上限之后，防止记忆烂成一锅粥的那条回路就是整理：**并重复、降过时、留痕迹**。

它的三条红线（都写在插件侧，不只是本文的君子协定）：

| 红线 | 含义 |
|---|---|
| **降级不删** | 旧条目 `status: active → superseded`，仍在库里、可回滚；整理从不物理删条目 |
| **桶内不跨** | 只合并同一个 `track × scope × agentKey`（workspace 层再加 `workspaceKey`）里的条目 |
| **模型可见 ⟺ 落盘** | 判断由**会话里的模型**做；插件本体不调 `ctx.llm`、不起进程（静态可核：21 个源文件零命中），写走审批门、落审计 |

理由：插件自己直调模型会成会话日志外的黑箱——审批载荷、审计行、会话日志三者拼不出「它到底改了什么」。所以语义判断是**会话里的模型**的活。

**后台轮不破这条红线**：它由系统计划任务唤起一个正常的无头**会话**（`dsh --profile headless`），插件本体依旧不调模型、不起进程；那轮会话与你现在这轮一样有审批载荷、有审计行、有会话日志。它只被允许走 `auto` 档（字面只差标点、空白或符号），`review` 档一律留着等人。

## 何时启动

**只由用户发起。** 触发不必卡死句式：

- 「整理一下记忆」「记忆太乱了，收拾收拾」「把重复的合并掉」「yammory tidy」
- 预热段末行或 `/memory tidy` 的提示说「该整理了」时，你可以**问一句**要不要整理

不启动的情形：用户只是在聊天里提到记忆；用户没要求而你判断「该清了」。整理会改多条条目、会弹审批，默认不跑。

用户中途喊停，立刻停，把已经写进去的报清楚。

## 一轮的形状

```
tidy 取计划（只读）→ 判「哪几条在讲同一件事」→ 分级器重跑硬杠定档
     → auto 档走 auto-tidy 落写｜review 档走 supersede（过一次审批）｜skip 档不动
     → 报告：降级了几条、合并成什么、下一轮建议
```

**你的判断只决定「提议合哪几条」；能不能不必过人眼就落写，由内核说了算。** 插件会拿库里的真实条目重跑一遍五根硬杠（同桶 / 条数 / 去标点后逐字一致 / 相似度 / 覆盖度），给出三档：

| 档 | 含义 | 落写走哪条 |
|---|---|---|
| `auto` | 够确定（去空白与标点**与符号**后逐字一致） | `action=auto-tidy`：不打扰审批，一次落一批 |
| `review` | 不够确定（相似度与覆盖度过线，但没达到 auto 的全部条件） | `action=supersede`：过一次审批，且**必须由人在场** |
| `skip` | 不合格（跨桶 / 超条数 / 相似度或覆盖度低于底线） | 不动 |

两条线要分清：**改写过的同义句落 `skip`**（字面几乎不重合，相似度 0.1 量级，连 review 线都够不着，原样留着）；**一字之差落 `review`**（相似度 0.9 在 auto 线以上，但逐字不一致，机器不替人赌）。两档都不自动合，但下场不同：一个原地不动，一个等你过目。硬杠名与阈值见 [`references/merge-rules.md`](./references/merge-rules.md) 第五节。

### 第 1 步：取计划

```
memory { action: 'tidy' }
```

用户也可以自己跑 `/memory tidy [--days=N]` 看同一份计划（命令面只读，不写库）。

计划里有什么，怎么用：

| 字段 | 意思 | 你该怎么用 |
|---|---|---|
| `backlog.due` / `reason` | 是否过开工线（字符 / 条数 / 12 小时兜底） | 未过线且用户没要求 → 不建议动手 |
| `buckets[].candidates` | 热度窗口内（近 7 天更新，或召回次数高）且**没带 `merged` 标**的条目 | 只有这些可以被合并；带 `merged` 标的已整理过，跳过 |
| `buckets[].pairs` | 桶内两两 Jaccard ≥ 0.5 的**线索**（含相似度） | 线索不是结论：从相似度最高的往下看，逐个自己判 |
| `buckets[].batchHint` | 该桶建议分几批（每批 ≤20 条） | 一次 `supersede` 最多 20 个 id |
| 桶键 | `track/scope #agent @workspace` | 桶键不同的条目**永远不要放进同一次调用** |

### 第 2 步：判「是不是同一件事」

判据（至少满足一条才合并）：

| 判据 | 例 |
|---|---|
| 同一主体 ＋ 同一谓词，只是措辞不同 | 「偏好中文回复」／「回答尽量用中文」 |
| 一条是另一条的特例或子集 | 「偏好中文」＋「除英文技术术语外都用中文」 |
| 两条各说一半，合起来才完整 | 「周三下午没空」＋「周四上午也没空」 |

**不算同一件事**的反例：

| 反例 | 为什么不算 |
|---|---|
| 只是共享关键词 | 「喜欢 Rust」与「不喜欢 Rust 的宏」共词却立场相反 |
| 只是同一个领域 | 「数学考了 90 分」与「数学老师姓王」— 同一个领域，两回事 |
| 时间点不同、都在描述当下 | 「现在住 A 城」与「现在住 B 城」是**冲突**，不是重复（走分面裁决，别自作主张合并） |
| 一条是承诺、一条是事实 | 「答应周五交」与「周五没交」— 并存才有意义（落差本身是画像） |

### 第 3 步：落写

**先看内核给你判了哪一档**——同一批 id 与文本，`tidy` 计划里没有这一档，得由 `auto-tidy` 自己判：

```
memory {
  action: 'auto-tidy',            // 只接受 auto 档：非 auto 一律拒绝、零落盘
  ids: ['<id1>', '<id2>'],        // 2..5 个（分级器上限 5），必须同桶
  text: '合并后的一句话'            // 必填：分级器拿它跟真实条目比逐字一致
}
```

两档各有各的路：

| 档 | 怎么落写 | 说明 |
|---|---|---|
| `auto` | `action=auto-tidy` | 不打扰用户；被拒时错误里带 `failed gates` 与两个数值，据此判断差在哪 |
| `review` | `action=supersede` | 过一次审批（与人工整理同一道门）；**不要在后台轮里用它** |
| `skip` | 不落写 | 计划里的相似线索只是线索，不是结论 |

`supersede` 的入参（`review` 档走这条）：

```
memory {
  action: 'supersede',
  ids: ['<id1>', '<id2>'],        // 1..20 个，必须同桶（取自 tidy 计划）
  text: '合并后的一句话',           // 省略 = 只降级、不落新条目
  facet: '心智',                   // 可选：新条目的画像坐标（原条目有就带上）
  level: 6,                       // 可选
  tags: ['observation']           // 可选：`merged` 标由插件自动补
}
```

两条路共同的规矩：

- **一次审批一批**（`auto-tidy` 在后台免审，靠粒度写策略放行）；被拒就如实说哪几条没写成，**不换措辞重试**。
- 产出条目自动带 `merged` 标 → 下次整理见到就跳过（收益判据由标机械判出）。
- 旧条目变 `superseded`：仍在库里、按 id 查得到、审计行只记 id（`text: null`）。
- 每批落一个**批次号**，贯穿产出条目、降级条目与全部审计行；`/memory restore --batch=<批次号>` 可整批撤回。
- 每批收尾落一行 `audit(action='consolidation')` 变更摘要——这就是整理回执。

### 第 4 步：报告

给用户一句话：降级了几条、合并成了什么、还剩下哪些桶没动（以及为什么）。**不要复述全部原文**，也不要给「记忆质量评分」。

## 纪律（宁少勿多）

1. **拿不准就不并**。合并错了要靠 `restore` 救回（`memory` action=`restore`，或 `/memory restore <id...>`），成本比留下两条重复高。
2. **一次只处理你确信的那几组**。计划里有 10 组线索，只做 3 组是正常结果，0 组也是合法结果。
3. **不许新增原文没有的信息**。合并只能是对既有条目的压缩与去重；出现新事实就是编造。
4. **不许把冲突当重复，也不许自己判方向**。两条互相矛盾时调 `memory` action=`arbitrate`（方向由面表决定：能力听观察、意愿听自陈、其余五面两条都留并各打 `gap` 标）；工具不接受反向参数，也别试图绕过。
5. **不跨桶、不超过 20 条/批、不物理删**——这三条插件会拒，别去试边界。
6. **本会话不自动跑**。没有用户开口，最多问一句。（后台轮是另一条路：系统计划任务到点唤起无头会话，那条路只走 `auto` 档、且不由你在这里发起。）

## 边界

- v1 只做**增量整理**（热度窗口内）；全库整理与排队式按钮留 v2。
- 整理只动**当前会话可见集**：别的工作区、别的 agent 的条目既看不到也合不了（插件会拒）。
- **插件本体**不调模型、不起后台进程、不加定时器；触发检测（`agent/turn-stopping`）只读算积压，过线只给提示。
- **后台轮不是插件的一部分**：它由系统计划任务在空闲时段唤起一个无头会话（`dsh --profile headless`），跑的是与本会话同一套判据、同一套硬杠、同一个库。插件只提供入口（`auto-tidy`）与放行口（粒度写策略 `source:tidy-auto`）。

## 后台轮（无人值守的那条路）

系统计划任务到点唤起无头会话时，那条会话拿到的指令就是这个 skill 的简化版：

```
tidy 读计划 → 有 auto 档的组就 auto-tidy 合并 → 没有就什么都不做
```

它与你在场时的差别只有三点：只用 `auto-tidy`（**不碰 review 档**）、写入来源标为 `tidy-auto`、被拒时只留一行 `*-denied` 审计而不会有人来改判据。所以你在这里定判据时多想一步：**只要不能落 auto，就不该指望后台帮你合**。
