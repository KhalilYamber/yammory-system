## Why this exists

Способный помощник остаётся помощником с амнезией. Каждую сессию он начинает заново: он не знает, что вы уже понимаете собственные векторы, но ни разу не касались тензорной сети, что вам приятнее, когда вас поправляют, а не подбадривают, и что три недели назад вы решили не идти этим путём. Поэтому вы заново представляетесь ему, раз за разом, а разговор, который мог начаться с интересного места, начинается с нуля.

`yammory_system` даёт DeepSeek Harness место, где эти знания хранятся, и способ пользоваться ими без догадок. Три вещи отличают его от склада памяти:

- **Он решает, как говорить, ещё до поиска.** Профиль из семи граней несёт уровень знаний по каждому предмету, поэтому помощник знает, какую лексику вы выдержите, ещё до того, как отвечает: вставка происходит при сборке запроса, а не после шага поиска.
- **Без вас ничего не записывается.** Каждый путь записи принудительно проходит через собственный шлюз одобрения DSH внутри сервиса. Отклонённая запись тоже оставляет след; молчаливая запись — состояние, недостижимое для этого плагина.
- **Вы можете проверить его работу.** Всё, что видел модель, занесено в журнал, хранилище — обычный файл SQLite, который можно просматривать, выгружать и проверять, а целая категория ошибок предотвращена устройством, а не дисциплиной.

## Install

```sh
# 1. install the bundle into your profile
dsh plugin --profile web add "github:KhalilYamber/yammory-system#main"

# 2. restart, then verify the row
dsh --profile web --dump-config | grep -A3 'id: yammory_system'
```

Другие каналы и удаление:

- **канал git** (последний `main`): `dsh plugin --profile web add git+https://github.com/KhalilYamber/yammory-system.git`.
- **канал tarball**: выполните `npm pack` в этом репозитории, затем `dsh plugin --profile web add ./yammory_system-<version>.tgz`.
- **удаление**: `dsh plugin --profile web remove yammory_system` (база памяти и журналы сессий сохраняются).

## How it works

`yammory_system` — это шов возможностей, а не ещё один склад памяти: типизированный сервис `ctx.memory`, локальный провайдер SQLite (`node:sqlite`, WAL, `0600`, в `$DSH_HOME/dsh-memento/memory.db`) и его потребители — инструмент `memory` и замороженный снимок, вставляемый в системный запрос.

Две дорожки × два слоя × ключ по агенту: дорожка `user` (факты о пользователе) и дорожка `agent` (факты об окружении и соглашения), каждая разделена на слои `user-global` и `workspace` с изоляцией по `agentPreset`. Снимок замораживается один раз за сессию при первой сборке запроса и больше в её ходе не меняется. Блок прогрева несёт речевые ограничения и постоянный профиль, а закрывается строкой-указателем (`N more workspace / agent-track entries stay out of this block`), чтобы модель знала, что есть что подтянуть через `memory_recall`: число занимает одну строку, содержимое остаётся по требованию.

## Capabilities

- **Шлюз одобрения нельзя обойти.** Каждый путь записи (`add` / `replace` / `remove` / `seed`) принудительно проходит через водопад одобрения внутри сервиса, а не в слое инструментов. `writePolicy: ask | auto | off` — конфигурация, невидимая для модели; `replace` / `remove` / `consolidate` несут в запросе на одобрение полный текст изменяемых записей, а отклонённая запись всё равно оставляет строку аудита `*-denied`.
- **Видно модели ⟺ занесено в журнал.** Вставленный снимок дословно попадает в `system/message`; любую запись можно восстановить из `approval/asked` + `approval/decided` + собственной таблицы аудита плагина.
- **Ограничено и честно.** Мягкие предупредительные линии на дорожку и слой (по умолчанию user 2000 / agent 4000). Их пересечение никогда не блокирует запись — оно лишь отмечает, что слой стоит укрупнить. Никогда не усекается, никогда не сжимается автоматически.
- **Переключатель на сессию.** У каждой сессии есть свой переключатель памяти (собственная таблица SQLite плагина, схема v6; по умолчанию включён). Выключенный означает: вставка прекращается (замороженный блок прогрева отбрасывается сразу), припоминание отклоняется (`SESSION_MEMORY_OFF`), записи отклоняются на том же слое, что и шлюз одобрения, а канал наблюдения не сканирует сессию и не выбирает её как историю. Управляющее чтение (`/memory list` / `budgets` / `audit` / `export`) остаётся доступным. Переключайте через `/memory session on|off` или переключателем в заголовке; само состояние переключателя никогда не попадает в журнал сессии, а его строки аудита несут `text: null`.
- **Наблюдайте, и пусть наблюдение идёт само.** Канал наблюдения читает ограниченный срез ваших собственных прошлых сообщений и пишет поведенческие записи, до которых анкете не дотянуться.
  - **Будильник.** Проверка только для чтения отмечает, когда последнее наблюдение старше недели: одна строка аудита `observe-due` плюс строка в конце следующего блока прогрева.
  - **Раунд без присмотра.** Еженедельный запуск по расписанию может провести его в ОДНОМ рабочем пространстве: безголовая сессия `dsh` сканирует, выводит не более трёх записей с доказательствами и фиксирует их через тот же шлюз одобрения, что разрешено собственным источником политики записи (`source:observation`, `auto` / `ask` / `off`).
  - **Где живёт расписание.** Внутри плагина нет таймера; это запись в планировщике заданий Windows, ровно как и для раунда упорядочивания.
- **Упорядочивание и измерение.** Проход упорядочивания под управлением модели сливает записи, говорящие одно и то же, в одну запись с тегом `merged` и понижает старые до `superseded` — они остаются на диске, вне поля зрения любой сессии, и никогда не удаляются. Он никогда не пересекает корзины (`track × scope × agentKey`, плюс `workspaceKey` на слое workspace) и никогда не запускается сам.
  - **Кто решает.** Пять механических жёстких ворот (одна корзина / число участников / буквальная идентичность после снятия пунктуации, пробелов и символов / схожесть / покрытие) решают, можно ли записать слияние без участия человека, — и никогда уверенность самой модели. Без ручной проверки может пройти только тот ярус, члены которого идентичны после снятия пунктуации, пробелов и символов; полностью перефразированная пара получает оценку `skip` и остаётся на месте; изменение в один символ получает оценку `review` и ждёт вас.
  - **Фоновый раунд.** Безголовая сессия `dsh`, разбуженная вашим собственным планировщиком, сливает механически однозначные дубликаты и оставляет остальное. Запись закрепляет собственный источник аудита (`tidy-auto`), так что гранулярная политика записи может разрешить ровно этот один путь, пока все прочие записи остаются за шлюзом одобрения.
  - **Отметки, а не действия.** Проверка `agent/turn-stopping` только для чтения лишь отмечает, что очередь перешла черту: одна строка аудита `tidy-due` плюс строка в конце следующего блока прогрева.
  - **Числа.** `/memory stats` показывает коэффициент повторов, долю попаданий припоминания и объём вставки, в том числе в выдвижной панели. Доля успеха намеренно оставлена пустой: в этом репозитории нет источника сигнала о том, «действительно ли вставленный блок прижился».
  - **Кнопка на панели.** **Упорядочить всю библиотеку** теперь действительно выполняется: один щелчок ставит метку (`tidy_requests`, схема v7) и запускает безголовую сессию, которая читает план и сливает то, что ей позволено, затем снимает метку и оставляет идентификатор пакета. В выдвижной панели остаются одна строка состояния (`pending` → `running` → `done` · объединено групп: N, либо `nothing needed merging`, а при сбое `failed` с кнопкой повтора) и кнопка отката для блока пакета — ни диалога, ни затрат контекста. Исполнитель **определяется**, а не угадывается по платформе (настроенный `tidy.exec`, иначе собственный лаунчер хоста, иначе `dsh.cmd` / `dsh` в PATH), и раунд, не оставивший пакета, всё равно оставляет собственную квитанцию `exited`, чтобы кнопка не могла остаться заблокированной. `tidy.enabled: false` возвращает поведение «только очередь».
- **Управляйте памятью: откатывайте понижение, разрешайте конфликт по грани.**
  - **`restore`** проходит понижение в обратную сторону (`superseded → active`, `version` не трогается, возвращение в поле зрения каждой сессии) и это единственный выход из пониженного состояния.
  - **`arbitrate`** разрешает случай, когда один факт несёт два источника: он решает по **одной грани**, а направление берётся из фиксированной таблицы — способность следует за наблюдением, предпочтение следует за самоотчётом, а остальные пять граней сохраняют **обе** записи и помечают каждую тегом `gap` (сам разрыв и есть доказательство). Таблица задаёт направление, поэтому обратного довода для передачи нет, а внутри группы сохраняется запись, обновлённая позже всех.
  - **Те же правила, что и для любой другой записи.** Тот же шлюз одобрения, тот же переключатель на сессию, те же правила корзин. След аудита: `restore` по записи, `arbitrate` по понижению (`text: null`, только идентификаторы), `arbitrate-tag` по тегу и одна закрывающая сводка `arbitrate` с именами тех, кого сохранили, кого понизили и почему.

## Configuration

Все настраиваемые параметры — поля Schemastery `Config` (изменяются из cordis.yml). Неверные значения громко падают при загрузке. Переопределение — под строкой `yammory_system`.

**Панель настроек.** Когда сервис настроек DSH смонтирован, каждое поле ниже (кроме `enabled`) редактируется из собственного пункта плагина **`yammory-system` в боковой панели настроек DSH** (раздел верхнего уровня, как «Общие» или «Плагины»); правки попадают в пользовательский слой настроек (`settings.yaml`) и не требуют правки файлов. Почти всё применяется на ходу (политики записи, язык, бюджеты, лимиты, предложения, панель, `dbPath` / `auditRetentionDays` через переоткрытие хранилища, `retrieval.vector` через подмену средства поиска) — только `snapshotOrder` требует перезагрузки DSH. Без сервиса настроек всё откатывается к собранной конфигурации cordis, ровно как раньше. Пункт памяти в боковой панели можно скрыть с той же страницы (`panel.enabled`).

| Key | Default | Meaning |
|---|---|---|
| `enabled` | `true` | Главный выключатель; `false` убирает сервис, инструменты, снимок, команду, панель и отвечающего (не редактируется со страницы настроек — у отключённого плагина нет пункта настроек) |
| `panel.enabled` | `true` | Показывать пункт памяти в низу боковой панели; сохранение `false` со страницы настроек скрывает его сразу, перезагрузка не нужна (сама страница настроек остаётся доступной) |
| `dbPath` | `''` → `$DSH_HOME/dsh-memento/memory.db` | Абсолютный путь или путь относительно `$DSH_HOME` (в Windows откат к `~/.dsh`) |
| `budgets.user.userGlobal` | `2000` | Мягкая предупредительная линия для слоя user-global дорожки user |
| `budgets.user.workspace` | `2000` | Мягкая предупредительная линия для слоя workspace дорожки user |
| `budgets.agent.userGlobal` | `4000` | Мягкая предупредительная линия для слоя user-global дорожки agent |
| `budgets.agent.workspace` | `4000` | Мягкая предупредительная линия для слоя workspace дорожки agent |
| `writePolicy` | `'ask'` | Политика записи по умолчанию: `ask` / `auto` / `off` (невидима для модели) |
| `writePolicies` | `{}` | Переопределения по дорожке/области или по источнику (например, `user/workspace`, `source:claude`) |
| `language` | `'en'` | Язык, видимый модели, и язык вывода команд: `en` / `zh` |
| `snapshotOrder` | `-50` | Порядок секции снимка (после идентичности harness, до персоны) |
| `maxEntriesPerQuery` | `20` | Предел результатов на запрос по умолчанию (жёстко ограничен 1000) |
| `commandListLimit` | `50` | Сколько записей выводить на `/memory list` / `query` |
| `commandAuditLimit` | `10` | Сколько строк аудита выводить на `/memory audit` |
| `recall.historyLimitDefault` | `8` | Сколько сессий сканирует `memory_recall` по умолчанию |
| `recall.snippetCap` | `5` | Сколько фрагментов на сессию у `memory_recall` |
| `recall.snippetChars` | `300` | Длина фрагмента у `memory_recall` в символах |
| `recall.windowDays` | `30` | Окно свежести `memory_recall` в днях |
| `observe.days` | `14` | Окно `memory_observe scan` в днях (жёстко ограничено 90) |
| `observe.sessions` | `8` | Сколько недавних сессий берётся на скан (жёстко ограничено 20) |
| `observe.perSession` | `12` | Сколько сообщений берётся на сессию, с равномерным разбросом, чтобы уцелели и начало, и поздние поправки (жёстко ограничено 20) |
| `observe.messageChars` | `400` | Предел символов на сообщение до усечения с многоточием (жёстко ограничен 800) |
| `observe.totalChars` | `12000` | Бюджет символов на весь срез; скан останавливается на нём и сообщает, что не успел покрыть (жёстко ограничен 30000) |
| `recall.weighting.heat` | `0.3` | Потолок надбавки за нагрев (множительная; `0` выключает её). Нагрев = припоминания (с насыщением) × затухание по периоду полураспада с момента последнего припоминания, так что память должна припоминаться снова и снова, чтобы не остыть |
| `recall.weighting.heatSaturation` | `10` | Сколько припоминаний насыщают надбавку за нагрев |
| `recall.weighting.heatHalfLifeDays` | `14` | Период полураспада нагрева в днях (запись, которую давно не припоминали, остывает) |
| `recall.weighting.freshness` | `0.2` | Потолок надбавки за свежесть (множительная; `0` выключает её) |
| `recall.weighting.freshnessHalfLifeDays` | `30` | Период полураспада свежести в днях |
| `recall.weighting.tagDiscount` | `0.5` | Вес токена, когда он совпал только с `tags` (совпадение по телу записи даёт `1`) |
| `retrieval.vector` | `false` | Переключатель семантического припоминания: `true` подменяет припоминание на векторное **только если зарегистрирован действительно семантический провайдер эмбеддингов** — хеш-провайдера или подделки намеренно недостаточно, ведь он не моделирует смысл и молча обнулил бы припоминание для CJK. Иначе остаётся поиск по ключевым словам без зависимостей (разбор CJK на биграммы, совпадение по любому токену, взвешивание по нагреву и свежести, ранжирование по релевантности) |
| `panelEntriesLimit` | `200` | Размер страницы записей в веб-панели |
| `panelAuditLimit` | `20` | Сколько строк аудита веб-панель показывает по умолчанию |
| `auditRetentionDays` | `0` | Хранение аудита (0 = хранить вечно) |
| `proposals.enabled` | `true` | Автоматически снимать предложение памяти после каждого успешного сжатия |
| `proposals.maxChars` | `2000` | Предел символов предложения |
| `proposals.maxPending` | `8` | Предел предложений в ожидании |
| `tidy.enabled` | `true` | Действительно ли **Упорядочить всю библиотеку** запускает фоновый раунд: `false` возвращает прежнее поведение (только метка, в ожидании следующей сессии) |
| `tidy.profile` | `'headless'` | Имя профиля исполнителя, которым пользуется фоновый раунд |
| `tidy.exec` | `''` → определяется автоматически | Точка входа исполнителя: пустое значение означает «разобраться на месте»: сначала собственный лаунчер хоста (скрипт CLI, которым он был запущен, под тем же node), затем `dsh.cmd` / `dsh` в PATH; настроенное значение (абсолютный путь или ваш собственный скрипт запуска) перекрывает оба. Промах честно сообщается как «исполнителя не удалось запустить», с кнопкой повтора |
| `tidy.timeoutMs` | `480000` | Окно ожидания: раунд убивается, если к тому времени не завершился, и сообщается как «timeout» (минимум 30 секунд) |
| `tidy.task` | `''` → встроенный текст задачи | Перекрывает инструкцию, передаваемую безголовой сессии (только конфигурация, не в карточке настроек) |

## MCP server

`yammory_system` поставляет **MCP-сервер** stdio только для чтения (`yammory_system-mcp`), чтобы внешние MCP-клиенты (Claude, Codex, …) могли искать в хранилище памяти без harness. Он говорит на JSON-RPC 2.0 поверх JSON с разделением переводом строки (NDJSON) — один объект JSON на строку, без обрамления `Content-Length`.

**Только чтение.** База открывается через `node:sqlite` с `readOnly: true` (никаких миграций, никаких записей WAL, никакого прироста счётчика припоминаний); отсутствующая база возвращает пустые результаты, а не падает.

| Tool | Purpose |
|---|---|
| `memory_search` | `{query, limit?}` → ранжированные записи (подстрока без учёта регистра через шов Provider поиска) |
| `memory_stats` | `{}` → число записей `{total, namespaces}` + обзор по дорожкам и областям |

Запуск напрямую:

```sh
node bin/mcp-server.mjs
# or, through the GitHub channel: npx -y -p github:KhalilYamber/yammory-system yammory_system-mcp
```

Путь к базе задаётся через `$DSH_MEMENTO_DB_PATH` (абсолютный или относительно `$DSH_HOME`); по умолчанию `$DSH_HOME/dsh-memento/memory.db`.

Пример для Claude Desktop (`claude_desktop_config.json`):

```json
{
  "mcpServers": {
    "yammory_system": {
      "command": "npx",
      "args": ["-y", "-p", "github:KhalilYamber/yammory-system", "yammory_system-mcp"],
      "env": {
        "DSH_MEMENTO_DB_PATH": "/home/you/.dsh/dsh-memento/memory.db"
      }
    }
  }
}
```

`npx` находит пакет здесь через канал GitHub (в реестре npm этого репозитория нет), так что именно спецификация `-p github:…` его и забирает.

Сервер работает только на чтение: без сети, без записей, без шлюза одобрения — только поиск и статистика.

## Permissions & data

- **Разрешения**: объявляет `harness:tool`, `filesystem:read`, `filesystem:write` и `network:none` / `subprocess:none` / `shell:none` / `python:none` / `credentials:none` в своём манифесте мастерской. Одобрение записи идёт через официальный шов одобрения. Читать это буквально следует с одной оговоркой: кнопка **Упорядочить всю библиотеку** запускает одну одноразовую безголовую сессию (`dsh --profile headless`) — единственный запуск процесса у плагина, инициируемый пользователем, с журналом в собственном файле, с откатом по пакету и с возможностью отключения через `tidy.enabled`.
- **Данные**: локальная база SQLite (`0600`), ноль сети, ноль учётных данных.
- **Журнал сессии**: полнота аудита складывается из пары одобрений (`approval/asked` + `approval/decided`) плюс собственная таблица аудита плагина.

## Security boundaries

- **Только публичные сервисы.** Потребляет `tools`, `systemPrompt` и шов одобрения; никаких изменений движка, цикла агента, apiproxy или официального UI.
- **Ноль сети, ноль учётных данных.** Локальная база с правами файла POSIX `0600`.
- **Падать громко.** Повреждённая база, более новая схема или неверная конфигурация падают при загрузке; неоднозначные совпадения подстроки падают со структурированными ошибками. Пересечение предупредительной линии никогда не проваливает запись.
- **Один процесс — одно хранилище.** Несколько сессий делят хранилище SQLite; два процесса с одним `$DSH_HOME` пишут один и тот же файл (побеждает последний записавший, при блокировках SQLite).

## Known limitations

- **События сессии объявлены, но ещё не излучаются (rc.2).** `memory/added|updated|removed|recalled|snapshot` объявлены на уровне слияния, но в rc.2 нет поверхности регистрации для типов событий вне репозитория; излучение включится, когда какая-нибудь сборка harness их зарегистрирует.
- **Фоновый раунд упорядочивания видит одно рабочее пространство.** Первые ворота читают только те сессии, чей `cwd` совпадает с `cwd` вызывающего, поэтому раунд, запущенный из панели, покрывает тот рабочий каталог, откуда его запустили (плюс слой user-global). Другие рабочие пространства ведут собственные раунды.
- **Политике `ask` нужен отвечающий.** Если ни один отвечающий UI/ACP не собран, записи падают в закрытое состояние.
- **Индекса FTS5 нет.** Поиск подстроки идёт по `instr` без учёта регистра (корректно для CJK).
- **Наблюдение — это белый список, и у белого списка есть край.** `memory_observe scan` оставляет только события `user/message`, у которых `source.kind` равен `user` или `user-rpc`; по замерам на этой машине это отбрасывает 48% всех событий `user/message` (контекст времени выполнения, AGENTS.md, каталоги навыков, раунды целей, уведомления субагентов). Он, однако, не может отделить сообщение, набранное человеком, от пришедшего через внешний мост, который тоже объявляет `kind: 'user'` — этот вид и есть единственный сигнал, который несёт журнал. Считайте одну процитированную строку слабым доказательством; требуйте повторения между сессиями.
- **Та половина поиска, что называется «семантической», пока не семантическая.** `retrieval.vector` включается только с провайдером, объявляющим себя семантическим, а единственный поставляемый здесь провайдер объявляет `false`, так что сегодня переключатель по устройству откатывается к припоминанию по ключевым словам. Для настоящего семантического припоминания нужен источник эмбеддингов, который этот репозиторий не выбрал.

## How it's different

| Plugin | What it is | yammory_system's difference |
|---|---|---|
| dsh-mneme | саморазвивающаяся память с широким набором возможностей | только профиль малого корпуса: он состязается речью на измеренном уровне пользователя, а не расширением возможностей |
| dsh-meow-memory | хранилище из семи слоёв с поиском BM25 | никакой инженерии поиска: таблица уровней по предметам плюс арбитраж граней |
| dsh-persona-memory | вставка персоны в запрос | на слой глубже: **уровень знаний по каждому предмету** и **арбитраж граней** поверх постоянного профиля |
| dsh-memory-evolve | склад памяти и циклы эволюции | типизированный шов сервиса, шлюз одобрения и аудит по журналу сессий; амбиций склада нет |
| dsh-mnemon | помощник хранилища памяти | протокол + шлюз + аудит, а не ещё одно хранилище |
| dsh-kb-sieve | просеивание базы знаний | никакой инженерии поиска: поиск подстроки по малому корпусу, припоминание между сессиями через `session_search`/`sessionQuery` |
| dsh-tdai-memory | инструменты памяти под задачи | бюджеты заданы на дорожку×слой и обеспечиваются сервисом, а не «как получится» |
| claude-bridge | мост к Claude Code | родной для DSH; будущий путь `seed(source:'claude')` позволит мосту питать то же хранилище |
| dsh-external/Recall | память внешнего агента | локальность в первую очередь, ноль сети, идёт через собственный шов одобрения DSH |
| Official MCP memory examples | заявленная позиция DSH «память = внешний MCP» | **родное первопартийное** дополнение: та же цель, без внешнего сервера; оба сосуществуют |

Два различия, которые держатся против сегодняшнего поля, — последняя пара в таблице выше: **профиль из семи граней, несущий уровень знаний по каждому предмету** (он решает, как помощник говорит, ещё до всякого поиска), и **арбитраж граней** (он решает, как разрешается конфликт двух источников: способность следует за наблюдением, предпочтение следует за самоотчётом, остальные пять граней сохраняют обе записи и помечают каждую тегом `gap`).

Имя — **`yammory_system`** (устанавливается из канала GitHub; в реестре npm его нет). Не `dsh-recall` (легко спутать с dsh-external/Recall) и не удалённое прежнее имя `dsh-memory`.

## dsh-memory-protocol v1

`yammory_system` — это общественная репетиция протокола памяти DSH, кандидатная форма официального шва `ctx.memory`. Протокол нормализует шов этого плагина в межплагинный контракт:

- **Спецификация записи** — две дорожки × два слоя × ключ по агенту, плюс короткие `tags` (≤16 × ≤32 символов) и `version` у каждой записи, растущая при каждом `replace`.
- **Семантика записи** — идемпотентные условные записи по уникальной подстроке; полезные нагрузки «одобряй то, что видишь» (`replace` / `remove` / `consolidate` несут полный текст того, что меняют).
- **Контракт аудита** — любую запись можно восстановить из `approval/asked` + `approval/decided` + журнала провайдера.
- **Модель предупредительных линий** — мягкие предупредительные линии на слой / семантика `AMBIGUOUS_MATCH`.
- **Версионирование схемы** — правила миграции с громкими проверками версии.

- **Spec** — [docs/protocol-v1.md](docs/protocol-v1.md) (中文: [protocol-v1.zh.md](docs/protocol-v1.zh.md)); нормативная JSON Schema в [docs/schemas/dsh-memory-protocol-v1.schema.json](docs/schemas/dsh-memory-protocol-v1.schema.json).

**Реестр адаптеров** — `ctx.memoryAdapters` (`register` / `list` / `adapt` / `export`) позволяет сторонним плагинам памяти говорить на этом протоколе, регистрируя чистый преобразователь данных (обратимый `register()`; импорт идёт через `seed` за шлюзом одобрения, экспорт — только чтение). Подключение: [docs/adapters-guide.md](docs/adapters-guide.md) (中文: [adapters-guide.zh.md](docs/adapters-guide.zh.md)).

| Built-in adapter | External format | Notes |
|---|---|---|
| `mem0` | коллекции фактов mem0 (`{facts: [{memory, metadata?}]}`) | `metadata.category` / `metadata.tags` становятся тегами; необработанные массивы `messages` отклоняются — адаптеры преобразуют, но никогда не извлекают |
| `hermes-memory-md` | Hermes `memory.md` (`## section` + пункты списка) | имена секций становятся тегами; проза вне пунктов списка громко падает |
| `claude-code-memory-md` | markdown в стиле `CLAUDE.md` (заголовки, пункты списка, абзацы) | пункты списка и абзацы становятся записями; имена секций становятся тегами |

**Набор проверок на соответствие** — [test/protocol-conformance/](test/protocol-conformance/README.md): распространяемый набор случаев, который прогоняет любой провайдер, заявляющий совместимость (`node test/protocol-conformance/run.mjs --provider ./your-factory.mjs`); CI этого репозитория прогоняет его против собственного провайдера как эталонного образца (`npm run test:conformance`).

- **Предложение в апстрим** — [docs/upstream-proposal.md](docs/upstream-proposal.md) (中文: [upstream-proposal.zh.md](docs/upstream-proposal.zh.md)): почему официальному шву `ctx.memory` стоит принять протокол, в чём различия и каков путь миграции.

## What we learned from the terminal memories

`yammory_system` не является портом Claude Code, Codex или Hermes — но его устройство намеренно впитало то, что каждый из них сделал верно, и отказалось от того, что вредило:

| Terminal memory | What it got right | What yammory_system adopted |
|---|---|---|
| **Claude Code** — `CLAUDE.md` | иерархические файлы памяти в виде простого текста (уровень пользователя → уровень проекта), читаемые и правимые человеком, автоматически вливаемые в каждую сессию | записи простым текстом; слои `user-global` / `workspace`, вливаемые каждую сессию; хранилище, которое можно просматривать, `export` и проверять — прозрачность как свойство |
| **Codex** — `AGENTS.md` | инструкции с областью действия по каталогам, обнаруживаемые автоматически и вставляемые без трения для модели | слой `workspace` с ключом по cwd сессии (в Windows без учёта регистра); замороженный снимок, вставляемый автоматически при старте сессии |
| **Hermes** — `memory.md` | упреждающие сохранения памяти и урок безопасности: шлюз, обеспеченный только в слое инструментов, обходится поздней вставкой инструментов | инструмент `memory` с подсказками «сохранить/пропустить» + автоматически снимаемые предложения за шлюзом одобрения; шлюз живёт внутри методов записи `ctx.memory`, а не в слое инструментов |

А от чего отказались намеренно: скрытое автосжатие в приватное для модели состояние (сводки сжатия здесь становятся **предложениями в ожидании**, которые ждут решения человека «одобрить/отклонить»), амбиции склада и векторного хранилища, и любая запись без видимого человеку одобрения или следа аудита. Заимствовано и другое: документированная оговорка Hermes о том, что два процесса с одним домашним каталогом пишут один и тот же файл памяти, — см. «Security boundaries».

## Development

```sh
npm install              # node ^22.19 || >=24
npm test                 # node --test: 484 tests
npm run lint             # oxlint
npm run test:conformance # dsh-memory-protocol v1 conformance suite
npm run typecheck        # tsc --checkJs gate
npm run check:coverage   # line-coverage gate
npm run check:readmes    # five-language README consistency gate
npm run verify:self-contained # reject out-of-repo dependency specs
npm run verify:artifacts # artifact presence + syntax + import
```

`lib/` не имеет зависимостей от DSH (только встроенные модули node:); импорты DSH есть только в `index.mjs`.
