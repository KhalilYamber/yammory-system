# 红队第二轮修复方案（0914-18 战报的 6 条）

> 来源：`0914-18` 只读红队的可复现清单（2 高危 ＋ 4 中危），病灶统一为**静默不一致**——库、审计、会话可见集三处说法对不上。
> 纪律：修法要**响亮失败**，不许把「静默丢失」换成「静默容忍」。

## 0. 结论先行

| # | 级别 | 问题 | 修法 |
|---|---|---|---|
| **高 1** | 🔴 | `supersede` 的合并条目**漂出源桶**（`agentKey` 取自写方会话，共享记忆被静默收进某 agent 专属，单向不可逆） | 合并条目的 `agentKey`/`workspaceKey` **继承源桶**（`targets[0]`），仅当 `input` 显式给定才覆盖 |
| **高 2** | 🔴 | `arbitrate` 的 `kept` 在并发下可以是**假话**（审批窗口内 champion 被降级，仍返回 `ok:true` 并写「kept X」审计） | 审批后**重新校验 champion 仍 active**，否则响亮失败（对齐 `supersede` 的不变量） |
| **中 1** | 🟠 | 「能力听观察」可被**两步 `replace` 翻转**（facet 是模型可写的，方向表再硬也拦不住改输入） | **只在文档登记**为设计边界，不硬堵（每次 facet 改写都有审批与审计留痕） |

| **中 4** | 🟠 | `export → import` 往返**静默丢** `tags` / `facet` / `level` | 导出投影补 `facet`/`level`；导入映射搬 `tags`/`facet`/`level`（与现有 `validateMemoryEntry` 一致） |

## 1. 逐条设计

### 高 1 · 合并条目继承源桶

- 现状：`lib/protocol.mjs` `supersede` 里
  `const agentKey = input.agentKey || this.#agentKeyOf(write)`（会话推导）→ 合并条目落写方会话的 agentKey。
- 改：**目标桶由 `targets[0]` 决定**（`assertSameBucket(targets)` 已保证同桶）：
  ```
  agentKey     = input.agentKey     ?? targets[0].agentKey
  workspaceKey = input.workspaceKey ?? targets[0].workspaceKey
  ```
- `input` 显式给定时仍以显式为准（保持既有跨桶覆盖能力，且 `#assertVisible` 会照旧校验）。
- 影响面：仅合并产出的新条目落哪个桶；源条目的降级行为不变。
- 回归点：**共享桶（`agentKey=''`）合并后仍落 `''`**；带 preset 的会话合并共享条目，产出仍是 `''`。

### 高 2 · arbitrate 的保留者审批后复检

- 现状：`kept=[champion]` 在审批前算好；落盘只对 `demoted` 侧调 `supersedeEntries`（其内部才校验 active）。
- 改：审批放行后、落盘之前，**复检 champion**：
  ```
  const fresh = this.store.entryById(champion.id)
  if (fresh === null || fresh.status !== ACTIVE_STATUS) throw new InvalidInputError(...响亮失败...)
  ```
  （`coexist` 面不涉及保留者，跳过此项。）
- 语义：与 `supersede` 的「审批期间目标变了就响亮失败」对齐；宁可失败让模型重来，也不写一句与库况相反的审计。

### 中 2 · enabled 严格布尔

- 现状：`index.mjs` 路由里只查键名存在，值用 `=== true` 判定 → 非布尔值一律被当成 `false`（关）。
- 改：`typeof input.enabled !== 'boolean'` → `400 { error: 'enabled must be a boolean' }`，不调用 `sessionSetEnabled`。
- 测试要覆盖：`"true"` / `0` / `null` / `{}` / 缺失 → 分别是 `400`（缺失已 400）／`400`／`400`／`400`。

### 中 3 · 会话开关的归属校验

- 先调研：DSH 的 `connection.fetch` handler 收到的 `Request` 是否携带**可校验的会话归属**（自定义头、cookie、或 connection 暴露的会话上下文）。**以 DSH 源码实际能力为准**。
- 若**有**：据它校验「请求声明的 sessionId == 请求所属会话」，不等即 `403`。
- 若**没有**（很可能）：退化为——
  1. **存在性校验**：`sessionId` 必须能在 `ctx.sessionQuery` 里查到（不存在的 id → `400`），挡掉「凭空造 id 关灯」；
  2. 审计行把来源 `source='panel'` 写实（现已写），并在文档**如实登记**：这是**同源内的越权面**（栅栏挡住外敌，同源只剩 DSH 自己的页面），属纵深防御，未彻底闭合。
- 无论哪条路，**报告里要写清实际落到了哪一档**，不许含糊成「已修复」。

### 中 4 · export/import 保真

- 导出投影（`index.mjs` 的 `export` 分支）：补 `facet`、`level`（`tags` 已有）。
- 导入映射（`import` 分支）：从文档条目搬 `tags` / `facet` / `level`（经 `normalizeTags` / `normalizeFacet` / `normalizeLevel`，非法值响亮拒绝）。
- 兼容：旧导出文档（无这三个字段）照常可导入（字段缺省 = 空/无坐标）。

### 中 1 · 文档登记

- 在 `ARCHITECTURE.md`（治理决策附近）与 `docs/记忆系统v2规格.md` 的相应处写明：
  > 「方向由表决定」是**裁决动作**的不变量；`facet` 仍是可写的普通字段，改写它需要**显式 `replace` ＋ 一次审批 ＋ 一条审计**。于是「把能力类改成意愿类再裁决」是**通的**——这是被审计留痕的显式路径，不是静默越权。若将来要堵，得让 `facet` 变成只能通过受控通道写的字段。
