# 记忆机制 v2 规格

> **一句话**：把「每轨每层的硬字符上限」换成「软预警 ＋ 分级注入 ＋ 静默整理」，让记忆库跟着对用户的了解一起长大，同时留住那股让系统收敛的力。
>
> **给后来人的注解**：本文出现的「积木 / 变形金刚」只是比方，不描述实现。落到代码里**没有新增实体层**，只有整理机在一次运行时做的一次判断。别照比方写码。

## 1. 为什么改

### 1.1 v1 长什么样

| 格（轨/层） | 上限 | 装什么 |
|---|---|---|
| `user / user-global` | 2000 | 跨工作区的用户偏好、习惯、雷区 |
| `user / workspace` | 2000 | 只在本工作区生效的记忆 |
| `agent / user-global` | 4000 | 跨工作区的环境事实与约定 |
| `agent / workspace` | 4000 | 本工作区的项目事实、已完成工作 |

规则三条：只数正文（标签、元数据不算，一个汉字算 1 字符）；写满**报错不截断**（`BUDGET_EXCEEDED`，报出当前用量与距上限还差多少）；上限可在设置页调。

这套东西**一行都不是本项目写的**，是基座 `dsh-memento` 原封带来的。上游的自我介绍第一句就是 *Bounded and honest*：「写满必须报错，绝不静默截断、绝不自动压缩」。它自己也在 README 里留了话：**中文场景按需调大并在 PR 说明理由**——放宽，本就是它预期的用法。

### 1.2 它错在哪

| # | 问题 | 说人话 |
|---|---|---|
| 1 | **代理变量太笨** | 用「字符数」近似「价值」。字符多的未必重要，字符少的未必无用。它逼着你删掉本想留的东西 |
| 2 | **与方向冲突** | 越了解一个人，记忆越庞大，这是正常的。一道固定的闸，等于给「更懂你」设了天花板 |
| 3 | **但它有用** | 这道闸是**全系统唯一的负反馈回路**。它的存在，让记忆库自己不会无限膨胀 |

### 1.3 所以，拆它是「一拆两补」

```
拆掉硬上限
   ↓ 失去收敛力
补① 整理机（静默整理）—— 新的收敛回路
补② 权重 / 检索 —— 让"按需"真的捞得回来
```

**这两条补不齐，拆闸就是让系统裸奔。** 顺序上，②宁可先行或同时，①可以稍后但要尽快。

## 2. 三条原则

| # | 原则 | 含义 | 反面（不做） |
|---|---|---|---|
| 1 | **无硬上限，留软预警** | 不再拒写。用量超线时**预警**，不打断写入 | 不做「写满报错」，也不做「静默截断」 |
| 2 | **分级注入** | 常驻一小段（稳、缓存友好）＋ 其余走按需池 | 不做「全量常驻」 |
| 3 | **不确定就并存** | 整理时没把握合并的，留在原处等下一轮 | 不做「强行消解冲突」 |

第 3 条与项目早先的**分面裁决**（能力听观察 / 意愿听自陈 / 落差两条都留）是同一个哲学。

## 3. 逐项规格

### 3.1 拆硬上限，改软预警

| 项 | 内容 |
|---|---|
| **要什么** | 写入**永不因容量被拒**。每格设一条**软预警线**，用量越线时在快照头 / 面板 / 审计里提示「这一格已 N 字符，建议整理」，但**不拦写** |
| **边界** | 预警是**提示**，不是限制。写满了也不报错、不截断、不自动压缩 |
| **现状** | `lib/budget.mjs`：`checkBudget()` 返回 `{ok:false,...}` 即拒写；`DEFAULT_BUDGETS`（`index.mjs:146`）给死四格上限；工具描述里写明「a write that would exceed it FAILS」 |
| **改造点** | ① `checkBudget` 的**语义从「拒」改「警」**（保留计算，改调用处行为）；② 新增预警线配置（默认取旧上限值，作为「该整理了」的参考线）；③ 快照头 / 面板 / `/memory budgets` 的文案从「用量/上限」改「用量/预警线」；④ 旧数据无缝：已存条目不动，只是不再被拒 |
| **可借的轮子** | 无直接可搬。开源框架（Letta / memobase）同样走「块有上限、写满报错」。**「无上限」这一步是自造**，参考价值在反面 |

> **一处提醒**：预警线只是**提示**，既不拦写、也不触发整理。真正触发整理的是 3.5 的**开工线**（那是「积压量」，量纲与这里的「存量」不同）。两者数值可以设成一样，也可以分开，但**概念上要分清**。

### 3.2 分级注入

| 项 | 内容 |
|---|---|
| **要什么** | 注入分两级：**常驻小段**（每会话首轮进上下文，保持小而稳）＋ **按需池**（其余全部，靠检索在需要时取回） |
| **边界** | 常驻段**必须小**，理由是缓存友好与注意力不稀释；用户可接受的**检索池**上限约 **10 万 token**（这是**池子**的规模，不是常驻段的规模） |
| **现状** | `lib/snapshot.mjs` 的 `renderWarmup`（预热段）＋ `residentEntries`；预热段按会话**冻结**（WeakMap），只取 `user 轨 × user-global`。工作区层与 agent 轨条目**刻意不进预热段**，走 `memory_recall` 按需取 |
| **改造点** | ① 常驻段内容**收窄**（先稳、先小）；② 把「工作区/agent 轨失去自动可见性」这条**欠账**（见 `施工清单.md`「已知未闭合项」#1）一并解掉——解法落在 S4 观察通道或情境触发 |
| **可借的轮子** | **Letta / MemGPT 的 core memory ＋ archival memory**，与本项同形：core 常驻上下文并可自编辑，archival 存外部按需检索。差别在它们给 core 设**硬上限**，我们改设**软预警** |

### 3.3 权重 / 检索（前置主梁）

| 项 | 内容 |
|---|---|
| **要什么** | 记忆按**任务相关度**分权重，按需取用时优先捞相关的。用户原话是「按需分配记忆在上下文里的权重」 |
| **边界** | 这是「拆上限」的**安全阀**。它不到位，拆闸就没有退路 |
| **现状** | 🟡 **零依赖半边已落地**（2026-09-14，`docs/检索加权方案.md`）。**层 A 已上线**（F2）：`KeywordRetriever` 为默认主路径（分词＋多词召回＋相关度排序）。**层 B 的零依赖半边已做**：权重公式（相关度 × 热度 × 新旧）落地为 `score = relevance × (1+heat·热度因子) × (1+freshness·新旧因子)`，热度因子 = 召回次数封顶 × **距上次召回的半衰期衰减**；匹配面扩到 `tags`（折权）；六个加权值经 Config `recall.weighting` 下发（设置页可改、热生效）；`retrieval.vector` 收口为「只认声明为语义的嵌入 provider」。**真语义半边仍未做**：`lib/embedding.mjs` 仍是伪向量 |
| **改造点** | ① 真语义检索（embedding）→ ⏸ **待「嵌入源」定夺**；② 多路召回 ＋ 重排 → ✅ 零依赖下只扩了**标签面**（语义路随 ①）；③ 权重公式（相关度 × 热度 × 新旧）→ ✅ 已落地（热度带半衰期衰减） |
| **可借的轮子** | **Hindsight** 的四路检索（semantic / BM25 / graph / temporal ＋ cross-encoder 重排）；**Mem0** 的向量 ＋ 图；**Letta** 的 archival search。这些多是 Python 实现，**借设计不借代码** |

> **红灯状态（2026-09-14）**：🟡 **已熄大半**。「按需真的捞得回来」的那半边（加权 ＋ 标签面 ＋ 开关收口）已上线；**真语义半边仍缺「嵌入源」**——那是一个**只有用户能做的决定**，不是工程量缺口。库还小的当下（个位数条目），keyword 已绰绰有余，故剩下那半盏灯是**潜伏风险而非现故障**。

### 3.4 会话级记忆开关

| 项 | 内容 |
|---|---|
| **要什么** | 每个会话一个开关：**这个会话用不用记忆**。关掉 = 三样全停（**注入停、召回禁、写入停**） |
| **边界** | 语义是「**这个会话，我不留痕**」，不只是「不注入」。因此还牵出 3.6 |
| **现状** | ✅ **已实现**（F5，2026-09-14）。方案 `docs/F5会话开关方案.md`；实现：`lib/store.mjs` 新表 `session_switch`（SCHEMA v5 → v6；只存「关」的行，重开即删行）＋ 三个方法（`sessionEnabled` / `sessionSetEnabled` / `disabledSessionIds`，非字符串/空 id 一律视作默认开）；拦截链五处——`MemoryProtocolCore` 六个写方法内部（与审批门同级、在 gate 之前，落 `session-off` 审计行且 `text: null`）、`index.mjs` 预热段（删该会话冻结缓存 ＋ 返回空段，不落 `snapshot`）、`memory_recall` 与 `memory.query`（`SESSION_MEMORY_OFF`，不检索、不 bumpRecall、不落 `recalled`）、`memory_observe.scan`（当前会话拒扫）＋ 选区（`disabledSessionIds` 先滤后截断，被滤条数计入账单 `scanned.skippedOff`）。管理面只读子命令不受影响；`import` 与提案 approve 属写，经协议层自动覆盖。条目不按会话隔离这一事实未变（隔离维度仍是 `轨 × 层 × agent`），开关拦的是「这个会话的读写与观察」，不是给条目分区 |
| **改造点** | ① 一条命令（如 `/memory session off`）→ ✅ `/memory session [on｜off｜status]`；② 会话标题栏槽位（UI 开关）→ ✅ `conversation.session.header.actions`（session scope，`sessionId` 从 standard props 取；紧挨 Agent 预设）＋ `GET/POST /api/memento/session`（走 `ctx.connection.fetch`，与面板同栅栏，同 path 合并为一条按 method 分派）；③ 状态**存插件自己的库**（按 `sessionId` 记）→ ✅ `session_switch` 表 |
| **红线** | 状态**不得写进会话日志**。项目已记录：往会话日志写自定义事件会让该会话下次加载被持久化层拒绝（`memory/*` 事件未获注册面） |
| **默认值** | ✅ **默认开**（F5 落实）：无行即开，表里只保留 `enabled=0` 的「关」行；常量锚点 `SESSION_DEFAULT_ENABLED` |
| **可借的轮子** | **OpenHanako（Hana）** `lib/memory/session-derived-state.ts`：提供「按 sessionId **原子作废**会话派生记忆」的完整范式——同时作废会话摘要与删除该会话的事实，且**已编译的聚合记忆刻意留在事务之外**。可直接照此形状设计开关的失效路径 |
| **路由收口**（0914 红队② 中 2 / 中 3） | ✅ `enabled` 严格布尔（非布尔 `400`，不落库、不回显假值）；`sessionId` 过 `session-query` 存在性校验（查不到 `400`）；审计来源写实为 `panel`。⚠️ **同源内的归属越权面未闭合**——DSH 侧没有服务端可校验的会话归属，详见本文 3.8 |

### 3.5 静默整理机

这是 v2 最重的一块。它接手 Dream 的活，从「备忘录」扶正为**承重机制**（**S6 Dream 因此并入本项，不再单列**）。

| **现状** | ✅ **v1 增量版已实现**（F6，2026-09-14）。方案 `docs/F6F7施工方案.md`；实现：`lib/consolidate.mjs`（热度选候选 / `merged` 跳过 / 桶分组 / 开工线积压）＋ `lib/protocol.mjs` 的 `supersede` 动作（同一个 `MemoryProtocolCore` 强制点：审批门 ＋ 开关 ＋ 落盘 ＋ 审计）＋ `lib/store.mjs` 的 `supersedeEntries`（事务内批量降级，可选同时落合并条目）＋ `memory` 工具的 `tidy`（只读计划）/ `supersede`（合并 ＋ 降级）＋ `index.mjs` 的 `/memory tidy` 与 `agent/turn-stopping` 只读积压检查 ＋ `skills/yammory-tidy/`。**语义判断由当前会话的模型做**（与 S4b 观察通道同款范式）——不新增后台进程、不新增定时器、不新增 `ctx.llm` 直调（那会成会话日志外的黑箱，撞「模型可见 ⟺ 落盘」）。**v1 只做增量整理**：全库整理与排队式按钮、缓冲/让路（那是给后台并发准备的，v1 无后台）、Dream 一概不做 |
|---|---|
| **改造点** | ① 触发：`agent/turn-stopping` 只读算积压量，过线**只给提示**（`tidy-due` 审计行 ＋ 下一个会话的预热段末行），**绝不自动跑**；真整理由 `/memory tidy` 或用户开口显式发起 → ✅ 已落；② 降级不删 → ✅ `status: active → superseded` 已接通（回滚留 S5）；③ 打标 → ✅ 整理产出恒带 `merged` 标；④ 桶内不跨 → ✅ 协议层响亮拒绝跨桶批次；⑤ 分批 → ✅ 单批 ≤20 条、一次审批、一个事务；⑥ 摘要/审计 → ✅ 每批一行 `consolidation`，降级行 `text` 恒为 `null`（只记 id） |

#### 3.5.1 触发与择时

```
写空闲 → 若「久未整理」则开工 → 整理（增量 / 手动全库）
       → 整理期间新来的记忆先进缓冲、不落主库
       → 整理收尾 → 缓冲灌回主库
```

| 项 | 内容 |
|---|---|
| **判据** | 用「**写空闲**」，不用「会话空闲」。冲突只在写上，不在说上——没有新的记忆在产生，且确实久未整理，就开工 |
| **检测挂点** | 挂在 `agent/turn-stopping`（一轮将结束时）检查一次。**不上新定时器**（守 S4「v1 不加定时器」的裁定） |
| **开工线** | 自上次整理以来的**新增/变动量** ≥ 2000 字符（或 ≥ 10 条），另加 **12 小时兜底** |
| **收工线** | 整理期间**缓冲里待落库的量** ≥ 400 字符（约两三条）时，整理**立即收工落库** |
| **硬顶** | 缓冲 ≥ 2000 字符时**强制中止整理、立刻落库** |
| **防抖动** | 整理一收工，两个积压量**归零重新攒**，攒够才二次开工。不另引回滞 |

> 数值都是**可调默认**，不替用户钉死。

#### 3.5.2 双向让路

「整理优先级高于写入」说的是**让路**，不是**加锁**：

- 写入者先让整理过（新记忆进缓冲区，不动主库）；
- 缓冲满了，整理**让回来**（先落库，下次再来）。

| 项 | 内容 |
|---|---|
| **整理硬超时** | 超过上限即中止，已改的按事务回滚 |
| **缓冲水位** | 超硬顶必须先落库、让整理收工 |

#### 3.5.3 判定：这条记忆**是否在描述这位用户**

取代原来的「是不是百科式内容」判据。

| 判据 | 处置 |
|---|---|
| **在描述用户**（哪怕含公共知识） | **留**。「用户最喜欢的乐队是 Radiohead」含公共知识，但它是画像 |
| **纯公共知识、不指向用户** | 丢 |
| **公共知识与用户信息捆绑** | 看捆绑是否成立。用户的个人经验、偏好、交集**在**，则留 |

> **这是 v2 最容易翻车的地方**。原设计想用「百科占比 60%」一刀切，被否决：那个 60% 是拍出来的数字，没有可验证定义，会误伤画像，且不可逆删除与 soft delete 原则打架。改用「是否描述用户」后，判据可解释、可复核。

#### 3.5.4 合并与置信

| 项 | 内容 |
|---|---|
| **要什么** | 把散落各处、其实在讲同一件事的记忆聚起来合成一条；**没把握就先不并**，留在原处等下一轮证据 |
| **置信度不足** | **并存**，不强拼。后续整理再判 |
| **合并错了** | 可拆开、可替换（由 soft delete ＋ 版本演进接住） |
| **形态选择** | **先走「当行为」**：整理时现场判断「这几条讲的是同一件事」，不新增长期结构。等哪天觉得「每次重判太费」，再考虑上「当结构」（存下谁和谁是一家） |
| **可借的轮子** | **Mem0** 的内部 LLM dedupe pass；**memobase** 的结构化画像演化（每次运行 LLM 调用上限 3 次）；**Hindsight** 的四杠杆框架（importance / merge / decay / eviction） |

#### 3.5.5 降级不删

| 项 | 内容 |
|---|---|
| **要什么** | 过时/错误的记忆**不物理删除**，标记降级（`status: active → superseded`），留痕可回滚 |
| **现状** | `entries.status` 列在 v5 已建（`store.mjs:861`，无 CHECK 约束），但**全仓没有任何写入路径**：`insertOne` 恒写 `active`（`store.mjs:705`），`replaceEntry` 的 UPDATE 不含 `status`（`store.mjs:355`）；`superseded` 只出现在常量、类型注与校验里。**有列，无行为**。降级语义留 S5，本次由整理机一并接住 → ✅ **F6 接通**（2026-09-14）：`store.supersedeEntries({ids, text?})` 事务内批量置 `superseded`，未知 id / 重复 id / 已降级目标一律响亮失败并整批回滚；读路径（`listEntries` / `queryEntries` / `matchCandidates` / `usage`）排除已降级条目，管理面走 `allEntries()`、按 `entryById(id)` 仍可查留痕。**只从 active → superseded**，回滚（superseded → active）仍留 S5 |
| **可借的轮子** | **Zep/Graphiti** 的时间边（`valid_at` / `expired_at` / `invalid_at`）；**Hindsight** 的 decay（置信度随时间衰减） |
| **回滚（S5 补齐）** | ✅ **已实现**（2026-09-14，S5 §1）：反向动作 `restore`——`store.restoreEntries({ids})` 事务内批量 `superseded → active`，**只允许这一个方向**（active 目标与未知 id 一律响亮失败并整批回滚）；协议层 `restore(input, write)` 走同一审批门与 F5 开关，审计记 `action='restore'` 行；工具面 `memory` action=`restore`、命令面 `/memory restore <id...>`。恢复的条目 `version` 不自增、`updated_at` 不动（它没被改写），回到会话可见集后重新计入预热段与预警线用量 |

#### 3.5.6 分批事务

| 项 | 内容 |
|---|---|
| **要什么** | 整理**分批写**，**每批原子**。宁可整成「半整理」，不留「改了一半、崩了」的烂摊子 |
| **现状** | 现成 `consolidate` 一次最多 20 条、一次原子写。全库整理会远超 20 条 |
| **改造点** | 循环分批，每批一次原子事务；批间可中断 |

#### 3.5.7 摘要 / 回执 / 审计

| 项 | 内容 |
|---|---|
| **摘要机制** | 每次整理后产出一份**变更摘要**（改了什么、删了什么、合并了什么）。**不弹窗**，可查、可回滚 |
| **缓冲回执** | 写入进缓冲时，工具**回「已排队」**（不阻塞回合）；整理落库成功再补一条；真落不下去就**响亮报错** |
| **铁律** | **不能有「既没写、又没人知道」的情况**——这正是用户最讨厌的静默失效 |
| **审计粒度** | 单独一条粒度键 `source:consolidation`：**不弹窗**（顺用户意），但有摘要 ＋ soft delete 可回滚 |

#### 3.5.8 整理边界：桶内不跨

| 项 | 内容 |
|---|---|
| **要什么** | 合并在**同一个 `(轨, 层, agent)` 桶内**进行 |
| **理由** | 不同桶语义不同（环境事实 ≠ 用户偏好）；跨桶合并会污染作用域；边界一划，整理机的权限面立刻变小、安全好审 |
| **与旧预算的关系** | 四格预算虽拆，但「**桶**」这个结构留着，当整理的**边界**用 |
| **状态** | ✅ **已定（用户拍板）**：桶内不跨 |
| **合并条目落哪个桶**（0914 红队② 高 1） | ✅ 新条目的 `agentKey` / `workspaceKey` **继承源桶**（`targets[0]`），与写方会话的 preset 无关——会话键只用来判断「本会话能不能看见」。此前取会话键：带 preset 的会话整理一次共享条目，就把共享记忆静默收进该 agent 专属（单向、不可逆） |

#### 3.5.10 热度公式

「最新」与「最热」常常不是一回事（刚写的还没被召回）。默认加权：

```
先按 updated_at 取近 7 天更新的，再按 recall_count 排序
```

**拍一个默认值，可配**。数值列入可调默认。

#### 3.5.11 收益判据与打标

整理机动手之前，先判一次「这条值不值得理」。

| 项 | 内容 |
|---|---|
| **收益判据** | 明显已经**结构化 / 组装过**的条目（例如多条已合成的一长条），**不再动手**——再次整理的收益低。整理只针对**明显零散**的记忆 |
| **打标** | 整理产出的条目标一个记号（如 tag `merged`），**下次整理见到就跳过**。这样「已整理」可由标机械判出，不必每次靠模型重新认 |
| **边界** | 标是「已整理」的信号，不等于「永不整理」。后续若有新证据，可清标重理 |
| **现状** | 无。`entries.tags`（JSON 数组）现成可承载此标，零 schema 改动 → ✅ **F6 落标**（2026-09-14）：常量 `MERGED_TAG = 'merged'`（`lib/protocol.mjs`），`supersede` 恒把该标并进合并条目的 tags（与调用方标签并存）；`lib/consolidate.mjs` 的 `selectCandidates` 见到即跳过，并在计划里报出「已整理 N 条」——收益判据由标机械判出。标是「已整理」的信号，不等于「永不整理」：清标重理留待后续 |
| **可借的轮子** | **OpenHanako** `lib/memory/dream/revision-store.ts`（修订存储）记录了「已修订」的状态，可参照它给「已整理」落一个可查、可回退的记号 |

### 3.6 会话开关与观察通道的关系

**问题**：关了记忆的会话，后台观察（S4）能不能读它的历史？

- 若读：用户在「关了记忆」的会话里说的话，转头被观察抽成画像，这是**背着他做的**，与开关的承诺相悖；
- 若不读：观察的原料池缩水，但这是**尊重**的代价。

**定论**：**关了记忆的会话，观察也不碰**。开关语义是「这个会话，我不留痕」，不只是「不注入」。✅ **已定（用户拍板）**。

> **一处副作用值得记下**：v2 把整理时机从「空闲检测」换成「存量判据」后，**会话开关不再是调度输入**，它退回成一件纯粹的**隐私/控制功能**。它原来扛的那份活，被警戒线接走了。

### 3.7 facet 的可写性（红队② 登记，0914）

**登记的是边界，不是漏洞的豁免。** 方向表（`ARBITRATION_BY_FACET`）管的是**裁决动作**的不变量：
`arbitrate` 只接受 `ids`，方向从表里查，调用方没有反向参数。`facet` 本身仍是条目的普通可写字段——
改写它需要一次**显式 `replace` ＋ 一次审批 ＋ 一条审计**（版本自增、写路径的每一道门都照走）。

于是「把能力类条目改成意愿类、再走裁决」这条路是**通的**。它是被审计留痕的显式路径，不是静默越权；
红队第二轮（`docs/红队2修复方案.md` 中 1）把它列为中危并接受「只在文档登记、不硬堵」的处置。硬堵
的代价是把 `facet` 从 `replace` 的入参里拿掉、只留受控升级通道——问卷与观察两条采集腿的正常改写
也要跟着另开通道，本轮不走这条路。若将来要堵，改法写在这里。

### 3.8 会话开关路由的两处收口（红队② 中 2 / 中 3，0914）

`GET/POST /api/memento/session` 是可写路由，红队第二轮在它身上撬出两条中危，收口如下：

| 项 | 收口 | 落档 |
|---|---|---|
| **`enabled` 非布尔** | 严格校验 `typeof enabled === 'boolean'`，否则 `400`，不落库、不回显假值（旧实现只认 `=== true`，字符串 `"true"` 被静默当成 `false` 落库） | ✅ 已闭合 |
| **无归属校验** | 按 DSH 源码核实：`connection.fetch` 的 handler 只拿到 `Request`，分发链不注入任何会话上下文；headers 由页面自己写、可伪造；browser-auth 是进程级凭据，不区分会话。**故没有服务端可校验的会话归属** | ⚠️ 退化为「存在性校验 ＋ 审计写实 ＋ 文档登记」，**同源内越权面未彻底闭合** |

退化档做的是：`sessionId` 必须能在 `session-query` 的逻辑会话语料里查到（查不到 `400`，挡掉「凭空造
id 关灯」）；审计行 `source` 写实为 `panel`（与命令面 `dsh-memento` 分开）。`sessionQuery` 未装配时
如实放行——那是「无从校验」，不是「校验通过」。**不硬造机制**：让页面自证一个归属头，不构成校验。

## 4. 可借的轮子（开源对照）

**先说一句实话**：这一批开源框架（Mem0 / Zep / Letta / Cognee / memobase）**几乎全是 Python**，且多绑自家 runtime。本项目是 **Cordis 插件的 JS 实现**，**接缝不同构**。所以能借的是**机制设计**，不是代码。搬轮子，搬的是图纸，不是零件。

**而最近、最同构的一份图纸，其实就在本机跑着——OpenHanako（Hana）自己。** 它的记忆系统在 `lib/memory/`，与本项目同一 JS 生态，且已经盖过 v2 想盖的每一间屋。对照如下。

| v2 机制 | 最像的开源实现 | 能借什么 | 借不动什么 |
|---|---|---|---|
| 静默整理机 | **OpenHanako 的 `lib/memory/dream/`**（`memory-units` ＋ `model-runner` ＋ `revision-store` ＋ `runner`，含修订/版本存储）＋ **memobase** ＋ **OpenDream** | 「读取→整合→写回」的闭环形态；记忆单元切分；调用次数封顶的省钱思路 | 它们的触发与存储都绑自家体系 |
| 整理的四类操作 | **Hindsight 四杠杆**：importance / merge / decay / eviction ＋ `aimemoryworks` 的 Merge/Supersede/Promote/Compress | 一套现成的**分类词汇表**，可作整理机设计的骨架与自检清单 | 四杠杆的实现细节（多依赖向量/图库） |
| 合并同类 | **Mem0** 的内部 dedupe pass | 「同实体合并、留更完整版」的判据 | 它偏 user-scoped fact，粒度不同 |
| 降级不删 | **OpenHanako** `lib/memory/dream/revision-store.ts`（修订存储）；**Zep/Graphiti** 时间边；**Hindsight** decay | 软删除 ＋ 版本/时间戳的字段设计 | Zep 需要 Neo4j |
| 分级注入 | **Letta / MemGPT** core memory（常驻可编辑）＋ archival memory（按需检索） | 两级结构的完整范式；「写满时提示腾挪」的交互 | 它们给 core 设**硬**上限，我们要改**软** |
| 权重 / 检索 | **Hindsight** 四路检索 ＋ 重排；**Mem0** 向量＋图 | 多路召回 ＋ 重排的架构；相关度×热度×新旧的加权思路 | 重排模型与向量库的部署成本 |
| 会话级开关 | **OpenHanako（Hana）** `lib/memory/session-derived-state.ts`：按 sessionId **原子作废**会话派生的摘要与事实，**已编译的聚合记忆刻意留在事务之外** | 「会话级记忆可整体作废、聚合层独立」的现成范式，与本项几乎同题 | 语言与运行时不同（TS/Electron vs Cordis 插件） |
| **无硬上限** | **无先例**。Letta core 写满报错、mem0 靠去重控量 | 只能反着看 | **自造，且是 v2 风险最高的一步** |

**结论**：整理机（3.5）、分级注入（3.2）与会话开关（3.4）**都有图纸可看**——最近、最同构的一份就在 **OpenHanako 自己**（`lib/memory/`）。拆上限（3.1）仍**没有先例**，靠自己。
