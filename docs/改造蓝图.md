# dsh-memento 改造蓝图报告

**任务理解**：要基于 Apache-2.0 的 dsh-memento（v0.5.12）改造出自家的 `dsh-user-memory`，核心诉求是把「自由文本记忆」升级成「七面多边形结构化用户画像」，把「冻结快照」升级成「预热分路 + 情境召回 + 表达约束」，把「模型触发写 + compaction 提案」升级成「问卷 + 观察」双通道，并给写入加 soft delete 与「观察优先于问卷」的冲突裁决。本文把这三处目标设计逐一对照现状源码，标出要动的文件和改法，全程只读不落盘。

**一句话核心结论**：dsh-memento 的「审批门 + SQLite + 审计 + retrieval seam」是可复用的骨架，但七面数据模型、分路注入、表达约束、soft delete 这四件事在现状代码里都不存在，必须动 `lib/store.mjs` 的表结构（SCHEMA v5）、`lib/snapshot.mjs` 的渲染、`index.mjs` 的快照段与采集监听，并新增问卷 skill 与观察离线分析通道。

## 一、模块地图

每个 `lib/*.mjs` 与入口文件各负责什么，一句话一个：

| 文件 | 职责 |
|---|---|
| `index.mjs` | 插件入口（唯一 host 面）：注册 ctx.memory 服务、审批 answerer、`memory`/`memory_recall` 工具、快照段、`/memory` 命令、面板路由、auto-capture 监听，DSH 依赖只允许出现在这里 |
| `types.d.ts` | 类型契约：`ctx.memory` / `ctx.memoryAdapters` / `memoryEmbedding` / `memoryRetrieval` 服务与 `memory/*` 会话事件声明合并 |
| `lib/constants.mjs` | 词汇表与协议常量：轨道（user/agent）、作用域（user-global/workspace）、错误码、SCHEMA_VERSION=4、硬上限 |
| `lib/errors.mjs` | 结构化领域错误：`code + details`，含 `BUDGET_EXCEEDED`/`AMBIGUOUS_MATCH`/`WRITE_DENIED` 等 |
| `lib/budget.mjs` | 每轨每层硬字符预算（纯函数）：usage、checkBudget、budgetReport |
| `lib/match.mjs` | 唯一子串匹配：零命中/多命中/恰一命中三态，replace/remove 定位用 |
| `lib/gate.mjs` | 审批门策略与 reason 编解码：ask/auto/off、粒度策略解析、reason 拼装/解析 |
| `lib/protocol.mjs` | 协议 v1 写语义核心 `MemoryProtocolCore` + 条目/导出信封/审计行校验（零 DSH 依赖） |
| `lib/registry.mjs` | 适配器注册表（register 可逆 / list / adapt / export） |
| `lib/adapters.mjs` | 参考适配器：mem0 / hermes-memory-md / claude-code-memory-md（纯转换，不调模型） |
| `lib/snapshot.mjs` | 冻结快照渲染（纯函数）：visibleEntries 过滤 + 按 track/scope 分组 + 用量头 |
| `lib/workspace.mjs` | 工作区键与 agent 键规范化（Windows 大小写不敏感） |
| `lib/extract.mjs` | 会话事件文本抽取（`memory_recall` 历史片段与 auto-capture 共用） |
| `lib/strings.mjs` | 模型可见/命令面双语词表（快照头/分组标题/提案头） |
| `lib/store.mjs` | node:sqlite Provider：entries 表 + audit 账本 + proposals 表 + 逐级迁移梯子 |
| `lib/retrieval.mjs` | 可插拔检索 Provider seam：SubstringRetriever（主路径）+ VectorRetriever（可选） |
| `lib/embedding.mjs` | 嵌入 Provider seam：确定性伪嵌入 `FakeEmbeddingProvider`（接口级，非语义） |
| `lib/mcp.mjs` | stdio MCP server（只读）：外部客户端（Claude/Codex）消费记忆库 |
| `bin/mcp-server.mjs` | MCP 独立进程入口 |
| `client/client.js` | Web 面板（零构建，只读：浏览/搜索/预算条/审计尾） |

## 二、差距清单

逐项对照「目标设计 vs dsh-memento 现状」，落到「要改的文件 + 改什么」：

| # | 目标设计 | 现状（dsh-memento v0.5.12） | 要改的文件 | 改什么 |
|---|---|---|---|---|
| 1 | 七面多边形固定板块画像 | 只有 `track: 'user'` 的模糊「用户画像」分组，条目是自由文本，无板块归属、无字段校验 | `lib/constants.mjs`、`lib/store.mjs`、`types.d.ts`、`lib/protocol.mjs` | 新增七面板块词汇常量；entries 表加 `facet` 列（SCHEMA v5）；`MemoryEntry` 加字段；校验 |
| 2 | 分领域知识水平（1-10 四档） | 完全不存在知识水平概念 | 同上 + 新字段/新表 | 存储每领域 `level`（整数）与 `tier`（四档枚举），或单独 profile 表 |
| 3 | 分路注入（预热 + 按需） | `snapshot.mjs` 一次性冻结全部可见条目 | `lib/snapshot.mjs`、`index.mjs` | 拆分渲染；systemPrompt 段改多段或加预热/约束分支 |
| 4 | 表达约束段 | 无表达约束，只有快照头 + 分组标题 | `lib/snapshot.mjs`、`lib/strings.mjs` | 新增约束渲染函数 + 词表 |
| 5 | 问卷通道（用户激发 skill） | 无问卷 skill；`memory` 工具是模型主动写 | 新增 skill 文件 | 新增问卷 skill（独立插件或本插件内 skill） |
| 6 | 观察通道（后台离线分析） | auto-capture 只把 compaction summary 存成 proposal，同步监听，不调模型、不做字段抽取 | `index.mjs`（`handleSessionEvent`）、`lib/extract.mjs` | 新增离线分析通道，产出字段化/知识水平评估 |
| 7 | soft delete 留痕（active/superseded，可回滚） | `remove` 是物理 `DELETE FROM entries`（`store.mjs:322`），无状态列 | `lib/store.mjs`、`lib/protocol.mjs`、`types.d.ts` | 加 `status` 列；remove 改 soft delete；回滚方法 |
| 8 | 冲突：观察优先于问卷 | 无优先级裁决机制；只有审批门 + replace 的 unique match | `lib/protocol.mjs`（写语义核心）、`lib/gate.mjs` | 写路径加来源优先级合并逻辑 |

几点需要说透的现状细节（避免误判）：

- **第 1、2 项的根因**：现状数据模型是「一条条自由文本」，`track/scope` 是唯一的结构化维度。七面多边形要的是「固定板块 + 面内可结构化字段」，这是质的差别，不是加个 `facet` 列就能自动完成，还要决定「每面是一个条目还是一个结构化文档」。
- **第 7 项的根因**：`replace` 已有 `version` 自增（SCHEMA v4，`store.mjs` 的 `replaceEntry`），能重建「同一条目」的演进史，但这是「同 id 的版本链」，和 soft delete 的「active/superseded 双状态 + 可回滚」是两回事。现状 `removeEntry` 是物理删除，删了就没了。
- **第 3 项的可复用点**：`memory_recall` 工具 + `lib/retrieval.mjs` + `sessionQuery` 历史召回已经是「按需召回」的现成底座，分路注入的「情境按需」可以站在它上面，不必从零造。

## 三、三个重点改造点

### a. 数据模型：两轨×两层 → 七面多边形

现状（`lib/store.mjs` 的 `BASE_SCHEMA_SQL` + `V3_SCHEMA_SQL` + `V4_SCHEMA_SQL`）的 entries 表关键列：`track`（user/agent）、`scope`（user-global/workspace）、`workspace_key`、`agent_key`、`text`、`source`、`tags`、`version`。没有任何「面」的维度。

改法（按文件）：

1. `lib/constants.mjs`：新增 `PROFILE_FACETS = ['躯体', '心智', '价值与意愿', '能力与技能', '行为与习惯', '社会与处境', '经历与轨迹']`（英文枚举为源），并加四档 `KNOWLEDGE_TIERS`（科普/本科/硕士/专家）。
2. `lib/store.mjs`：新增 `V5_SCHEMA_SQL` 给 entries 加 `facet TEXT`（可空，agent 轨条目不填）与 `level INTEGER`（可空，1-10）。`SCHEMA_VERSION` 从 4 → 5，在 `migrate()` 梯子里追加 `if (current < 5)`。
3. `types.d.ts`：`MemoryEntry` 加 `facet` 与 `level`；`MemoryEntryInput` 同步。
4. `lib/protocol.mjs`：`validateMemoryEntry` 加 facet 词汇与 level 范围校验（与 `normalizeTags` 并列的字段校验）。
5. `lib/snapshot.mjs`：`groupEntries` 现在的分组键是 `track/scope`，要改成「七面」分组（user 轨 + facet 维度），`renderSnapshot` 按面渲染。

**一个必须澄清的设计点**：七面是「每条目标一个 face 标签」，还是「每个 face 是一个独立的文档/对象」？前者改动小（加列），后者要大改（新表或 JSON 列）。这直接影响 `store.mjs` 的表设计，已在第四节标注为不确定处。

### b. 注入：冻结快照 → 分路注入 + 表达约束段

现状机制在 `index.mjs` 986–1033 行：`ctx.systemPrompt.section` 的 `text` 回调在会话首次 assemble 时同步 `store.listEntries()` → `visibleEntries` 过滤 → `renderSnapshot` 一次性渲染成带用量头的冻结块 → `WeakMap` 按 Session 冻结。`lib/snapshot.mjs` 的 `renderSnapshot` 是全量、无路区分。

改法：

1. `lib/snapshot.mjs`：把 `renderSnapshot` 拆成至少两个纯函数：
   - `renderWarmup(entries, budgets)`：只渲染「普遍相关」的少量内容（如用户的核心身份、全局偏好、雷区——需要一个新的「预热标记」字段，或按 facet 白名单过滤）。
   - `renderConstraint(profile)`：把分领域知识水平翻译成一段「说话要求」文本（例：某领域 level≤3 用科普口吻、level 7-9 用硕士/专家术语）。
2. `index.mjs` 快照段：`text` 回调改为「预热段 + 表达约束段」两段拼接（或拆成两个 `systemPrompt.section`，用不同 `order`）。按需召回仍走既有的 `memory_recall` 工具 + `retrieval` seam，不塞进开场。
3. `lib/strings.mjs`：新增预热头、表达约束头、四档描述词表。

**冻结语义的取舍**：现状「冻结 = 前缀缓存稳定」是刻意的（ARCHITECTURE 决策 1）。分路后，「预热段」仍应冻结，「按需召回」天然不冻结（走工具）。表达约束段取决于知识水平是否会话内可变——若不变则冻结，若可变则每次重算，这也要定。

### c. 采集：proposals/extract → 问卷 + 观察

现状的「采集」只有两条：

- **模型写**：`memory` 工具（`makeMemoryTool`）+ `/memory` 命令，走审批门。
- **观察雏形**：`handleSessionEvent`（`index.mjs` 1041–1113）监听 `session/event` 火线，只在 `compaction/summary` + `compaction/end` 时把压缩文本截断存成 `proposal`（`kind: 'compaction-summary'`，track=agent/scope=workspace），**不调模型、不写记忆、不做字段抽取**，等待 `/memory proposals approve` 人工裁决。

`lib/extract.mjs` 只做「事件 → 文本」的机械抽取，没有「文本 → 结构化画像字段」的能力。

差距与新增：

1. **问卷通道（新增）**：现状无。需要新增一个「用户主动激发」的问卷 skill，产出结构化回答（七面逐项 + 各领域知识水平自评），再经 `service.seed` 或新写方法落库。落库复用现有审批门与审计链即可。
2. **观察通道（改造 + 新增）**：现状 `handleSessionEvent` 是同步、单会话、只取 compaction。目标要「后台离线分析历史对话」——需要新增：
   - 一个后台任务（或复用 `sessionQuery` 服务的会话历史读取，`index.mjs` 的 `recallHistory` 已有读取会话事件的现成代码）；
   - 一段「对话 → 画像字段/知识水平」的分析逻辑（现状完全没有，`lib/extract.mjs` 只做文本抽取，不做语义归纳）；
   - 冲突时「观察优先于问卷」的裁决，落在写路径（见治理）。

**关键诚实点**：dsh-memento 明确把「适配器只做转换、绝不调模型抽取」作为红线（`lib/adapters.mjs` 头注释），它的采集哲学是「模型在对话里直接写记忆」，**没有「后台分析历史对话并自动归纳画像」这条路径**。观察通道的「自动分析」是全新能力，不是改改 `extract.mjs` 能补上的。

## 四、风险与不确定处

如实标注，不编：

1. **七面多边形的落地形态未定**（最大不确定）：是「每面一个条目（加 facet 列）」还是「每面一个结构化文档/对象（新表或 JSON 列）」？目标设计没写死，这直接决定 `store.mjs` 的表改法和预算口径（七面是否各算一个预算层）。改造前必须先拍板。

2. **知识水平 1-10 与四档的映射边界未定义**：科普/本科/硕士/专家如何对应到 1-10（例：1-3=科普？4-6=本科？），以及「分领域」的「领域」粒度（按什么切分领域、领域清单是否固定）都没有，无法给出确定实现。

3. **soft delete 的语义未定**：superseded 条目是否仍占预算、是否进入快照/召回、回滚是「恢复到 active」还是「重建一条」？`removeEntry` 改 soft delete 后，现有的 `AMBIGUOUS_MATCH`/`BUDGET_EXCEEDED` 语义、以及 `consolidate`/`seed` 是否也走 soft delete，都要重新定义。审计链也要为「回滚」加新 action 类型。

4. **「观察优先于问卷」的裁决粒度未定**：是「同一板块」冲突还是「同一字段」冲突？观察是「覆盖」问卷还是「并存待人工」？现状完全没有优先级机制，需要新建一套冲突规则，且要能被审计还原（谁赢、为什么）。

5. **观察通道的「后台离线分析」依赖 harness 能力，需验证**：现状 `recallHistory` 依赖可选的 `sessionQuery` 服务（headless 下缺失）。后台离线批量分析历史对话，能否拿到「跨会话」的完整历史、是否有定时/触发机制（对应 dev 工具的 daemon-loop 形态），取决于 harness 提供的 seam，不能在只读审查里确认它一定可用。

6. **问卷 skill 的归属未定**：是 `dsh-user-memory` 插件内部的 skill，还是独立插件（经 `ctx.memory` 服务协作）？这影响 `cordis.patch.yml` 与发布面（`package.json` 的 files）。

7. **表达约束段的「冻结 vs 动态」未定**：若知识水平会随观察通道更新，表达约束段就打破现状「快照冻结 = 前缀缓存稳定」的假设（ARCHITECTURE 决策 1 与 `systemPrompt` 提供者必须同步的硬约束）。这是架构层取舍，不是纯代码改动。

8. **测试与五语 README 的连带成本**：`AGENTS.md` 红线要求「行为变更同步五语 README」+ 覆盖率门（lib ≥90%、index ≥85%）。任何 schema 改动都要同步 `test/` 与 `docs/protocol-v1.md`，否则 CI 门会挂。改造预算里要把这笔成本算进去。
