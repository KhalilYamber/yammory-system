## 1. F6 · 整理机（v1 增量版）

### 1.1 载体与轮子

| 缺什么 | 拿什么补 | 现状 |
|---|---|---|
| 语义合并 | **已有** `consolidate`（定位＋新文本＋原子写＋审批＋乐观锁） | ✅ 在用 |
| 降级不删 | `entries.status` 列（v5 已建） | ⚠️ **有列无行为** |
| 已整理标记 | `entries.tags`（JSON 数组） | ✅ 可承载 |
| 分批 | `consolidate` 单次 ≤20 条（`MAX_CONSOLIDATE_MATCHES`） | ✅ |
| 审计 | `audit` 表 ＋ `action` 字段 | ✅ |
| 回执/摘要 | 新 `audit(action='consolidation')` 行 ＋ 返回文本 | 新 |
| 触发检测 | `agent/turn-stopping` 钩子（**只读**） | 新 |

### 1.2 一次整理跑什么（v1）

```
取候选（热度：近 7 天 updated ∪ recall_count 高）
  → 跳过带 merged 标的条目（收益判据：已整理的不再动手）
  → 模型判断「哪几条在讲同一件事」（桶内：同 track×scope×agentKey）
  → 对每一组：consolidate 成一条（新条目带 tag 'merged'）
  → 被取代的旧条目：status = 'superseded'（留痕、可回滚，不物理删）
  → 分批：每批 ≤20 条，每批一次原子事务
  → 收尾：写 audit(action='consolidation') ＋ 返回变更摘要
```

### 1.3 触发（v1 只提示，不自动跑）

- 挂点：`agent/turn-stopping`，**只读**统计「自上次整理以来的新增/变动字符数」（开工线默认 ≥2000 字符或 ≥10 条，另加 12h 兜底）。
- 过线时不自动调用模型（那会成黑箱）；把「该整理了」放进**预热段末行目录**或**审计行**，由用户/模型决定何时发起。
- 显式发起：`/memory tidy`（命令）或 skill 引导模型调用整理。

### 1.4 v1 不做

- 不做全库整理（排队式按钮）、不做缓冲/让路（那是给后台并发准备的，v1 无后台）。
- 不做 Dream。
- 不做跨桶合并（**桶内不跨**，规格 3.5.8 已拍板）。

## 2. F7 · 可观测三数

### 2.1 三数定义

| # | 数 | 怎么算（零模型） | 数据来源 |
|---|---|---|---|
| ① | **重复率** | 条目两两相似度超阈值的对占比（tokenize ＋ Jaccard，O(n²)，语料小可接受） | `entries` |
| ② | **召回命中率** | 有命中的 recall 次数 ÷ 总 recall 次数 | 需在 `recalled` 审计上补记「零命中」行 |
| ③ | **注入量** | 预热段字符数（及估算 token）＋ 条数 | `audit(snapshot)` |

### 2.2 载体

`/memory stats`：纯读命令，打印三数 ＋ 简短解读。**不写库、不调模型、不落审计**（读命令与 `list`/`budgets` 同档）。

### 2.3 第三数的缺口（诚实标注）

「注入量-成功率」里的**成功率**没有现成信号源。它的本义是「注入之后，对方是否真的听懂了」（追问减少 / 首答即懂）。这需要一条**用户侧反馈通道**（例如会话里一个「这次听懂了吗」的轻量标记）。

**v1 只报「注入量」**，成功率一栏明确写「需反馈通道，待定义」，不拿别的东西冒充。
